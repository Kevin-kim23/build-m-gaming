## 4. 출력과 로그에서 재현해야 할 동작

- 일반 출력의 패턴 가림만으로는 부족하다. 실제 회사 로그인에서 인증 URL/세션 표식 누락이 발생했으므로 **로그인 모드와 배포 모드는 원문을 숨기고 고정된 상태만 출력**한다.
- 로그인은 완료/대기/실패 등의 검증된 고정 상태만 표시한다. 이메일이 포함된 성공 문장을 그대로 쓰지 않는다. 명령 종료0만으로 로그인 성공 처리하지 않는다. 인증 링크나 코드를 채팅에 복사하도록 안내하지 않는다.
- 배포는 승인된 함수 이름과 검증된 상태만 출력한다. 출력 문자열에 '성공'이 들어 있다는 이유만으로 통과시키지 않는다. 알 수 없는 경고는 원문 없이 중단하고 Node 버전/SDK 경고도 분류 후 중단한다.
- stdout/stderr, console, CLI logger, 예외/스택, 분할된 문자열·Buffer·ANSI 제어문자·줄바꿈·마지막 미완성 조각을 검사한다. 원문을 파일에 잠깐 썼다가 지우는 방법은 금지한다.
- CLI 기본/사용자 지정/회전 로그 경로에서 파일 생성 전 차단이 필요하다. cwd의 firebase-debug.log만 검사하는 것으로 충분하지 않다.
- 함수 탐색 자식 프로세스와 npm/빌드 출력도 원문이 부모를 통해 새지 않는지 검사한다. 자식에게 보호 설정이 자동 상속된다고 가정하지 않는다.
- 정상 사용자 로그인에 필요한 CLI 인증 저장소의 정상 동작과 디버그 로그를 구분한다. 인증 파일을 읽어 출력·복사하거나 모든 파일 쓰기를 차단하는 방식으로 대신하지 않는다. Google Cloud 감사 로그나 서버 로그 정책은 변경하지 않는다.

## 5. 재현 가능성·부족한 정보·위험

**판정: 문서의 보안 규칙을 목표로 새 도구와 테스트를 만드는 것은 가능하다. 문서만으로 회사 원본과 완전히 같은 동작·호환성을 증명하는 것은 불가능하다.**

부족한 정보:

1. 원본 요청 허용 목록의 정확한 HTTP 메서드/호스트/경로/query/body/updateMask/권한 바인딩 검사와 API 버전.
2. 원본의 모듈 가로채기 위치·로드 순서, fetch/http/https/다른 전송 경로·리다이렉트·자식 프로세스 처리 범위.
3. 요청별 서명 업로드 URL 신뢰 등록·유효 범위, 숫자 프로젝트/계정 이름의 메모리 대조, 관리형2계정 생성 예외의 세부 조건.
4. 원본 로그 파일 차단 범위와 반환값, 출력 허용 상태 목록·분할 버퍼 처리, 알려진 경고 분류 조건.
5. 원본11개 테스트의 구체적 입력·기대값, 실제 최초 경고 원문. SHA-256만으로는 복원 불가.
6. 집의 실제 현재 자원/권한 상태. 이는 도구 검증 후 사용자 로그인과 읽기 확인으로 해결하며 문서상의0개를 가정하지 않는다.

승인 후에는 설치된 고정 CLI 소스를 읽어 빠진 인터페이스를 구체화하고, 명시적으로 허용되지 않은 것은 전송 전에 막는 방향으로 구현한다. 이 과정에서 새로 필요한 권한·API·예외가 나오면 승인을 다시 받는다. 실제 요청을 한번 보내 보고 허용 목록을 넓히지 않는다.

위험은 두 방향이다. 넓게 허용하면 범위 밖 요청/출력이 새고, 좁게 만들면 정상 배포도 멈춘다. 문서와 다른 원본의 숨은 예외, CLI 호출 방식·로그 경로 변화, 이미 시작된 요청/서버 내부 작업은 특히 주의한다. 첫 차단 이후 새 요청을 막는 검사도 필요하지만 이미 전송된 요청을 되돌릴 수 있다는 뜻은 아니다. 가짜 테스트 통과는 실제 IAM·배포 성공·비용 상한 증명이 아니다.

**회사 PC 원본과 내일 비교해서 같은 동작인지 확인한다.** 이는 향후 비교 계획이며 완료 사실이 아니다. 2026-10-14에도 원본에 접근할 수 없으면 '원본 비교 미완료'로 남긴다. 원본과 해시가 다를 새 구현이므로 동작별 비교표/회귀 결과를 확인해야 한다. 회사 로그인/.env/도구 복사는 하지 않는다. 비교가 가능해져도 원본 반입은 별도 승인 없이 하지 않는다.

## 7. 사용자 승인 대상과 이후 순서

이번 '(나)'는 **집에서 문서 기반으로 새 보호 도구를 작성 → 가짜 자료/고정 CLI 오프라인 검사 → 비밀·개인 경로 검사 → 통과한 도구와 테스트를 tools/ 아래 커밋·푸시**하는 안이다. HOME_PC_HANDOFF의 예전B안(저장소 밖 보관)과 달리, 사용자 최신 요청에 따라 통과 후 Git 보관까지 포함하는 제안이다. 아직 승인되지 않았다. 이번에는 검토 문서만 Git에 남긴다.

예상 구성은 출력 보호·배포 요청 정책·배포 진입 보호·사용자 로그인용 안전 실행·읽기 도구3개·가짜 테스트·사용법이다. 외부 CLI 경로는 인수/일반 환경 설정으로 받아 개인 절대 경로를 소스에 박지 않는다. 구체적 파일과 검사는 승인 후 구현하면서 실제 결과로 확정한다.

사용자가 할 일은 **이 '(나)' 제작·검증·tools 보관 범위를 승인할지 결정하는 것 하나**다. 로그인이나 .env 값을 지금 입력하지 않는다. 승인 후에도 도구 검증이 끝나기 전에는 로그인/.env/배포를 진행하지 않는다.

그다음 순서: 사용자 직접 로그인 → 읽기 확인 → 서버 빈 상태 재확인 → Git/업로드 제외 확인 후 사용자 .env 작성 → 배포 명령 확정·최종 승인 질문. 서버가 비어 있지 않으면 최초 생성 배포를 중단한다. 현재 제작 승인은 배포 승인을 포함하지 않는다.

위험·되돌림: 지금은 설치된 로컬 프로그램과 문서만 있어 클라우드 되돌림은 없다. CLI는 새 전용 폴더에 격리돼 있어 사용을 멈출 수 있고, 삭제는 별도 요청 시 정확한 경로 확인 후 수행한다. 새 보호 도구가 실패하면 사용하지 않고 로컬 수정/검사부터 반복한다. 보호를 제거해 원본 CLI로 우회하지 않는다. 이후 부분 배포가 발생하면 실제 자원 확인 후 별도 승인으로 처리하며 임의 삭제하지 않는다.

운영 프로젝트 개별 접근/배포·비용 보호 연결·앱 로그인 시험·관리자 Invoker·main/claude 병합·방침 번호 변경 없음. 사용자 직접 로그인과 비공개 설정 원칙 유지.
