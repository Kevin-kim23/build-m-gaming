# 서버 배포 순서서 · 준비용 · 2026-10-12

**이 문서는 배포 실행 허가가 아니다.** 비용 보고 후 사용자가 별도로 승인하기 전에는 개발·운영 배포, Blaze 전환, 예산·함수·IAM·예약·콘솔 설정을 변경하지 않는다. 결제·예산·App Check/Play Integrity 콘솔 작업은 사용자 본인이 한다. 실제 Google 로그인도 사용자가 직접 하거나 테스트 전용 계정으로만 확인한다.

## 0. 배포 전 확인과 중단 조건

- [ ] 0.81.0 테스트·빌드와 Node 22 demo 에뮬레이터 검증 결과를 확인한다.
- [ ] 변경된 예상 비용과 호출량, 함수·예약·관리자 리소스 설정 후보를 보고한다. 월 20만 원 계획과 예산 알림이 자동 지출 차단을 뜻하지 않는다는 점도 설명한 뒤 승인받는다.
- [ ] 모든 명령에 프로젝트 ID를 명시한다. 개발은 **budae-kiugi-dev**, 운영은 **budae-kiugi-prod**다. demo 자료를 운영으로 가져오지 않는다.
- [ ] 사용자 본인이 API 키 제한, App Check·Play 연결, 계정 2단계 인증과 필요한 권한을 확인한다.
- [ ] 실제 사용자 기록과 개발 만렙 기록을 테스트 대상에서 제외한다. 테스트에는 기존 게임 진행이 없는 별도 계정만 사용한다.
- [ ] 배포 대상과 되돌릴 커밋, 테스트 계정 삭제 경로, 당일 확인 담당자를 기록한다. 계정 식별자와 비밀은 공개 Git에 쓰지 않는다.
- [ ] 이미 신고 자료가 있는 환경이라면 구형 사유별 문서를 조사하고 같은 닉네임 세대의 reportDedup 보강을 확인한다. 보강하기 전에는 신고 원문의 90일 만료 정리를 켜지 않는다. 현재 운영 서버가 미배포라는 전제를 다른 환경에 그대로 적용하지 않는다.
- [ ] 만료 삭제 후 maintenanceRuns의 두 작업 커서에도 해당 식별자가 남지 않는지 확인한다. 같은 만료 시각의 다음 문서, 실패 항목, 실행 중 다른 작업의 삭제, 재개 시 식별자 재저장 방지를 함께 확인한다. 커서 정리가 실패하면 원본 삭제 트랜잭션도 실패해야 하며 미완료를 완료로 보고하지 않는다.
- [ ] reportDedup의 targetUid·nicknameRevision 조회 색인을 준비하고 READY 상태를 확인한다. 저장소의 firestore.indexes.json은 설정 정의이며, 실제 적용 완료를 뜻하지 않는다.
- [ ] 관리자 기본 닉네임 부여·복원, 최소 중복 정보 정리, 계정 탈퇴 시 관련 자료 삭제를 에뮬레이터에서 재확인한다.

확인하지 못한 항목이 있으면 다음 환경으로 넘어가지 않는다.

## 1. 에뮬레이터

1. Node 22 실행 경로를 해당 명령의 PATH 앞에 둔다. 설치된 전역 Node나 운영체제 환경 변수는 바꾸지 않는다.
2. tools/prepare-server.mjs로 앱 공통 규칙을 복사하고, server 관련 단위 테스트를 실행한다.
3. Auth·Firestore·Functions를 **demo-budae-kiugi** 프로젝트와 지정한 로컬 주소의 포트 9099·8080·5001에서만 시작한다. 운영 인증 정보나 프로젝트에서 내보낸 자료는 가져오지 않는다.
4. tools/server-emulator-check.mjs와 준비 검증 도구로 합성 Auth 계정, 닉네임, 저장 충돌, 신고, 삭제·재시도, 예약 작업의 처리 함수를 검사한다. 합성 Auth 검증은 실제 Google 로그인 성공의 증거가 아니다.
5. 관리자 인증 단위 테스트에서는 잘못된 토큰 발급자·대상·주체, 플레이어 토큰, 누락된 설정을 거부하는지 확인한다. 실제 IAM 검증은 다음 단계에서 별도로 진행한다.
6. 운영체제 백업, 실기기, Play 증명 발급, Google 관리자 IAM은 에뮬레이터 테스트만으로 완료 처리하지 않는다.

## 2. 개발 프로젝트 — 승인 후에만

1. 사용자 본인이 개발 프로젝트의 결제·예산, 필요한 API와 권한을 준비한다. 프로젝트와 개발 앱 ID가 일치하는지 확인한 뒤, 클라이언트 직접 접근을 거부하는 규칙과 색인을 먼저 적용한다.
2. 승인된 사용자 callable 6개부터 배포한다. 구현 버전, Node 22, 서울 리전, 리소스, 허용 앱 목록을 확인한다. CLI가 예상하지 못한 함수 삭제나 추가 자원 변경을 제안하면 중단한다.
3. 관리자 함수는 allUsers·allAuthenticatedUsers 권한 없이 비공개로 배포한다. 정확한 audience와 단일 호출 주체를 설정한 뒤, 비관리자 거부와 관리자 성공을 모두 검사한다. 앱 사용자의 Firebase Auth custom claim으로 관리자 권한을 대신하지 않는다.
4. 사용자 본인이 테스트 계정으로 로그인 → 닉네임 등록 → 합성 진행 저장 → 다른 테스트 환경에서 불러오기 → 신고·처리·복원 → 계정 삭제를 확인한다. 실제 기기 진행을 복사해 사용하지 않는다.
5. 예약 함수는 사용자가 검토한 배치량·주기·권한으로 배포한다. 테스트용 실패를 만들어 재처리, 만료 경계, 중복 실행, 집계 로그를 확인한다. Cloud Scheduler의 실패한 실행 재전송과 개별 삭제 요청의 다음 주기 재처리는 서로 구분한다.
6. 처리 상한 도달이나 작업 적체가 2회 이상 반복되거나, 미처리 삭제가 24시간 이상 남거나, 권한 오류·색인 누락·예상 실행 시간 및 비용 초과가 발생하면 운영 진행을 멈춘다. 원인과 설정 변경 비용을 다시 보고한다. 여기서 24시간은 검증 중 확인 기준이며, 보관 기간이나 삭제 완료 보장 시각이 아니다.

## 3. 운영 프로젝트 — 개발 검증과 재확인 후

개발에서 검증하고 승인받은 같은 커밋·규칙·색인을 적용하며, 환경별 앱 ID와 관리자 설정을 구분한다. 최초 운영 검증에도 테스트 전용 계정만 사용한다. 일반 테스터, 개발 만렙, 과거 개인 저장 기록을 업로드하지 않는다.

앱 증명 발급, 닉네임 중복 방지, 동시 저장, 기기 백업, 전체 계정 삭제, 강제 닉네임 변경·복원, 무권한 요청 거부 중 하나라도 실패하면 사용 범위를 확대하지 않는다.

배포 직후에는 다음을 확인한다.

- 리전, Node 22, 권한과 예산 알림이 승인한 설정과 일치하는지
- 사용자 callable 6개, 비공개 관리자 함수 1개, 예약 함수 2개가 의도한 형태로 배포되었는지
- App Check 성공·거부, Firestore 직접 접근 거부, 운영 환경의 debug 우회 거부가 모두 동작하는지
- 로그에 신고 원문이나 인증 토큰이 남지 않는지
- 함수 실행 시간·횟수, Firestore 읽기·쓰기, Play Integrity 할당량이 예상 범위인지
- 삭제한 계정의 관련 컬렉션 자료가 남아 있지 않은지

구체적인 함수명과 노출 형태는 배포 진입점과 manifest 검증 결과를 대조한다.

## 4. Play 설치 경로

Play Integrity가 모든 설정에서 직접 설치를 금지하는 것은 아니다. 공식 기본값은 **PLAY_RECOGNIZED 필수**, **LICENSED는 기본 필수가 아님**이다. Play 전용 배포의 권장 설정은 둘 다 필수이며, LICENSED는 Google Play에서 직접 설치하거나 업데이트한 사용자에게 발급된다. [공식 설정 표](https://firebase.google.com/docs/app-check/android/play-integrity-provider)

출시 검증은 사용자가 Play 내부 테스트 트랙의 별도 검증용 빌드를 승인·업로드한 뒤, 테스트 계정으로 테스터 등록 링크에 참여하고 Google Play에서 설치하는 경로로 준비한다. 직접 설치한 APK나 PC 웹에서는 운영 서버 기능이 거절될 수 있다. 이 거절을 정상적인 Play 설치 성공 검증으로 대신하지 않는다. 개발용 debug provider는 개발 프로젝트에서만 별도로 검증한다.

**이번 작업에서는 검증용·최종 AAB를 생성하거나 업로드하지 않는다.** 내부 테스트용 AAB가 필요한 시점에 목적·버전·범위를 설명하고 사용자가 진행한다. 기존 0.77.1·0.79.0 AAB는 현재 증명 경로까지 확인한 완성본이 아니다. 사용자가 폰 검증을 계속 생략하면 실제 Play 설치 앱의 통과 여부는 미완료로 남긴다.

## 5. 중단과 롤백

- 데이터 손실, 타인 정보 접근, 인증 우회, 무권한 관리 조치, 삭제 누락이 보이면 검증을 중단하고 원인을 분석한다. 정상 사용자의 DB를 백업으로 덮어쓰거나 옛 저장으로 일괄 되돌리지 않는다.
- 예약 실행에 문제가 있으면 해당 작업을 일시 중지할 때의 영향, 특히 삭제·정리 대기를 사용자에게 알린다. 승인된 담당자가 중지하며, 미완료 삭제 요청과 중복 방지 기록을 지우지 않는다.
- 함수 코드는 검증된 커밋의 별도 checkout에서 같은 프로젝트의 필요한 함수만 다시 배포한다. 전체 Functions 배포는 불필요한 함수 삭제 위험이 있으므로 대상을 먼저 확인한다.
- 현재는 운영 첫 배포 전이므로 이전 운영 릴리스가 없다. 초기 실패 때 되돌릴 정상 서버가 이미 있다고 가정하지 않는다. 기능 노출이나 예약을 멈춘 뒤 수정 버전으로 재검증한다.
- 이전 0.80 서버 코드로 내리면 일일 신고 제한, 새 보관 자료, 관리 조치 정리가 빠진다. 단순 전체 롤백 대상으로 사용하지 않고, 보안과 저장 호환성을 유지하는 최소 수정 릴리스를 준비한다.
- App Check나 Firestore 직접 접근 거부 규칙을 끄거나 관리자 경로를 공개하여 장애를 우회하지 않는다.
- 잘못된 닉네임 조치는 관리자 revert 경로로 먼저 복원한다. 원래 이름이 다른 계정의 소유가 되었다면 덮어쓰지 않고 별도로 검토한다. 감사 기록이 만료된 뒤에도 자동 복원이 가능하다고 약속하지 않는다.

## Node 버전 차이와 남은 확인

server/package.json은 Node 22를 지정한다. 준비 PC의 전역 버전은 24.21.0이며, 공식 Node 배포의 22.23.3 Windows ZIP을 별도 작업 폴더에 받아 공식 SHA-256과 대조했다. 시스템 기본 Node는 변경하지 않았다.

google-auth-library 11.2.0은 이미 설치된 서버의 간접 의존성을 관리자 토큰 서명 검증용 직접 의존성으로 명시한 것이다. 해당 버전의 엔진 요구사항은 Node 22 이상이다.

단위 테스트와 Node 22 demo 에뮬레이터 실행 결과는 [검증결과](../검증결과.md)의 0.81.0 기록에 둔다. Windows·로컬 Node 22에서의 성공은 Cloud Linux, IAM, 실제 SDK 인증, 예약 실행 검증 완료를 뜻하지 않는다. 같은 코드의 색인, 리전, 동시성, 네트워크 오류를 개발 프로젝트에서 반드시 따로 확인한다.

참고: [Firebase 함수 관리](https://firebase.google.com/docs/functions/manage-functions), [예약 함수](https://firebase.google.com/docs/functions/schedule-functions).
