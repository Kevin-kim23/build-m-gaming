# 서버 비용 1차 추정 · 2026-10-12

현재 0.80.0 코드와 서울(asia-northeast3) 공식 단가로 만든 **사용량 시나리오**다. 실제 청구액이나 운영 측정 결과가 아니다. 사용자에게 예상 이용자 수를 아직 받지 않았으므로 규모별로 계산했다.

월 20만원은 사용자 지정 계획 기준이다. 이번 추정은 Blaze 전환, 예산 생성, 함수/예약 설정 변경 또는 배포 승인이 아니다. 1단계 콘솔 확인도 아직 남아 있다.

## 사용자가 볼 요약

| 하루 서버 이용자 | 월 함수 호출 | 함수 실행 + DB 작업료 | 통신·보관·정리·운영 예비비 포함 계획액 |
| ---: | ---: | ---: | ---: |
| 100명 | 27,000회 | 약 0원 | 약 0.6만~1.7만원 |
| 1,000명 | 270,000회 | 약 0~0.7만원 | 약 0.7만~2.6만원 |
| 5,000명 | 1,350,000회 | 약 1.8만~6.7만원 | 약 3.2만~9.6만원 |
| 10,000명 | 2,700,000회 | 약 4.6만~14.3만원 | 약 6.9만~18.7만원 |

핵심 작업료는 1달러=1,500원이라는 계획용 환산값을 썼다. 오른쪽 계획액에는 부대비용 가정과 10% 여유분을 더하고 1천원 단위로 올림했다. 환산값은 실제 환율 또는 Google의 원화 청구 SKU를 확인한 값이 아니며, 10%도 실제 세금 확정액이 아니다. 예비비는 이미 발생한 요금이 아니므로 소규모 테스트의 실제 청구는 표보다 낮을 수 있다.

**현재 수동 저장 구조에서 초기 테스트~하루 1,000명 정도라면 20만원 계획에 여유가 있는 시나리오다. 하루 1만명에서는 여유가 작다. 랭킹과 서버 진행 검증을 더한 최종 비용은 다시 계산해야 한다.**

## 계산 가정

- 월 30일, 하루 한 사람당 서버 기록 확인 3번 + 서버 저장 3번. 기록 확인 1번은 프로필 조회와 저장 조회, 총 2함수 호출이다. 두 기기 사용은 같은 계정 사용량에 합산한다.
- 현재 호출 제한은 계정당 최근 60초 조회 30/변경 10회. 이는 허용 최대치이며 위 표의 평균 사용량 가정과 다르다. 게임 터치·모집·전투는 서버 호출을 하지 않는다.
- 2세대 Functions, 서울, 1vCPU/256MiB, 최소 상주 인스턴스 0을 가정. 코드에는 region과 함수별 maxInstances 2만 지정되어 있다. 실제 배포 설정은 아직 없으며 변경하지 않았다.
- 함수 호출당 독립 실행시간 0.3~1초를 가정했다. 실제 측정값이 아니다. 동시 처리의 CPU 공유 절감은 적용하지 않았고, 시작·재시도·느린 외부 인증의 추가 시간은 기본 산식 밖이다.
- 무료 할당량을 다른 프로젝트가 쓰지 않는 가정. Cloud Run의 CPU/RAM 무료분은 결제 계정 단위이며, 서울 초수에서 무료 초수를 직접 빼지 않고 Tier 1 단가의 달러 할인액을 뺀다.
- 한 저장 원문 20KiB 가정. 메모리에서 새로 만든 freshState의 serializeSave 결과는 2,350바이트였지만 성장한 기록의 평균값으로 삼지 않았다. 실제 이용자 기록은 열거나 전송하지 않았다. 하루 저장 원문 6회 전송(저장 조회 3회 + 저장 응답 3회), 압축 절감 없음. JSON 부가 필드·프로필 응답 등은 예비비에 포함.
- 누적 미탈퇴 계정 수를 하루 이용자의 3배라고 가정. 현재/직전/최초 기록 3개, 문서 메타데이터·색인 등을 원문의 추가 100%로 임시 반영했다. 장기 보관 계정이 늘면 DAU가 같아도 저장 비용은 늘어난다.
- 호출 집계 정리는 계정당 하루 최대 3번 정리되는 모형: 문서당 스캔 읽기 1 + 재확인 읽기 1 + 삭제 1. 이는 비용 가정이며 예약 주기 결정/적용이 아니다.
- 계정 등록·신고·삭제·삭제 재시도와 90일 정리, 예약 실행 CPU, 콜드스타트, 추가 전송, 빌드/이미지/로그 등의 미측정분에 월 $3~10을 임시 예비비로 더했다. 이 금액은 사용량 산출치나 상한 보장이 아니다. 운영 측정 후 교체한다.
- 일반 Google 로그인 사용, SMS 인증 없음. 현재 범위에서 별도 유료 Auth 기능을 전제로 하지 않았다.

## 코드에서 확인한 작업 수

정상 요청에는 UID 호출 제한 트랜잭션 1읽기+1쓰기, Admin Auth getUser 확인이 공통으로 들어간다.

| 기능 1회 | Firestore 읽기 | 쓰기 | 비고 |
| --- | ---: | ---: | --- |
| 프로필 조회 | 3 | 1 | 삭제 상태·프로필·호출 제한 |
| 저장 조회 | 3 | 1 | 삭제 상태·저장·호출 제한 |
| 저장 | 4 | 3 | 최초 기록 또는 직전 백업 포함 |
| 닉네임 최초 등록 | 4 | 3 | 정상 등록 |
| 신규 닉네임 신고 | 7 | 2 | 중복 신고의 쓰기는 감소 |

따라서 기본 모형은 **1인/일 9함수 호출 + 30읽기 + 15쓰기**다. 관련 코드: server/request-security.js, server/profile-service.js, server/cloud-service.js, server/report-service.js. 트랜잭션 충돌·재시도와 실패 요청 비용은 별도로 늘 수 있다.

호출 제한으로 거절한 요청도 함수 실행·집계 조회 비용이 발생할 수 있다. App Check 거절과 maxInstances는 월 지출의 완전한 차단 장치가 아니다.

## 20만원을 넘을 수 있는 조건과 다음 확인

- 이용자 수뿐 아니라 서버 버튼 횟수, 실행시간, 저장 크기, 무료분 공유, 실패/재시도가 중요하다. 호출이 10배 늘면 소규모 이용자라도 표의 상위 규모와 비슷해진다. 호출 제한을 정상 사용량 예상으로 삼지 않는다.
- 랭킹 계산/조회/갱신, 서버가 게임 진행을 계산하는 검증은 미구현이므로 이번 표에서 제외했다. 3단계 설계 시 합산하고 사용자에게 다시 보고한다.
- Play Integrity 10,000회/일은 이용자 수나 함수 호출 수와 같은 수치가 아니다. 토큰 재사용/세션 갱신을 확인하고, 규모 확대 전 할당량을 검토한다.
- minInstances 상향은 대기 비용을 만들 수 있다. maxInstances 2는 함수별 제한이어서 6개 함수 합계 2개라는 뜻이 아니다.
- 예산 알림은 지출을 막지 않는다. Google의 서비스별 spend cap은 일부 서비스에 적용되며 Firestore까지 전체 합계 20만원을 보장하는 장치로 간주하지 않는다. 지원 범위/초과 가능성/중단 후 저장·삭제 영향은 [공식 문서](https://docs.cloud.google.com/billing/docs/how-to/budgets-spend-caps)를 기준으로 배포 승인 전에 구체화한다. 이번에는 생성하지 않았다.
- 삭제 재처리 주기·배치량·최대 실행시간, 배포 이미지 정리, 로그 보관, 알림 금액은 아직 미확정/미적용이다. 승인용 설정안에 각각 예상 비용과 기능 영향을 포함한다.
- 사용자 승인과 1단계 잔여 확인 후에만 테스트 전용 계정으로 실제 응답시간·전송량·청구 지표를 확인한다. 현재 운영 배포/실제 로그인/실기기/Node22 동등성은 미완료다.
