- 예약은6시간 간격120회/월 + 하루1회30회/월, 합계150회/월. Cloud Scheduler 작업2개가 결제 계정 무료3개 안에 있으면 job 자체는 무료지만, 실행·DB·Auth 비용은 별도다.
- 초기 실행마다 플랫폼 실패 재시도를2회 허용하므로 예약 전송은 최대450회/월 모형이다. 개별 삭제/정리 실패는 같은 실행에서 계속 반복하지 않고 다음 주기에 이어가며 미완료 요청을 버리지 않는다.
- 준비 리소스: 예약2개는 각1vCPU/256MiB, min0/max1/concurrency1, 실행timeout300초(작업시간 예산240초). 관리자1개는256MiB/min0/max1/concurrency1/timeout60초. 사용자6개 함수의 기존max2는 유지. 모두 **소스 후보이며 운영 적용은 승인 대기**다.
- 150회가 매번300초까지 실행되면45,000vCPU초, 450회면135,000vCPU초다. 서울 CPU+RAM 표시 단가로 무료분을 중복 차감하지 않은 추가 비용은 각각 약$1.55 / $4.65(원화 환산·10% 여유분 포함 약2,600원 /7,700원). 외부 Admin 인증 호출, DB, 추가 전송/시작 시간은 별도다.
- 만료 집계는 UID별 문서이므로 하루1번 정리 시 일일 이용자 규모의 유입을 소화해야 한다. 코드 배치 후보는 rateLimits/reportDaily 각12,000개, 완료삭제/완료신고/감사 각1,000개까지(하루 최대27,000개), 페이지100·동시정리10·240초에서 중단한다. 끝까지 처리할 수 있다는 실측 보장이 아니며 커서로 다음 실행에 이어간다.
- 삭제 재처리는 한 실행100계정, 계정별 관련 문서 삭제 최대200개/시도. 닉네임 변경 뒤 최소 중복자료 복구는 한 실행100작업, 작업별100문서로 제한한다. 최악 입력에서는 시간 예산이 먼저 끝날 수 있다.
- 정상적인 만료 유입이 실제 처리량을 계속 넘으면 비용표보다 보관량·미처리 기간이 늘어난다. limitReached 또는 적체가 반복되면 사용자 확대를 멈추고 배치/시간/주기 변경의 추가 비용을 다시 승인받는다.
- 삭제된 식별자가 작업 진행 위치에 남지 않도록 삭제 트랜잭션마다 예약 상태 문서2개를 추가로 읽고, 참조가 있을 때만 갱신한다. 작업 시작/체크포인트에서도 식별자가 있는 커서의 원본을 다시 읽는다. 따라서 이전 단순 정리 모형의 문서당2읽기는 최소4읽기(스캔1+원본1+작업상태2)로 늘 수 있고, 상태 변경 쓰기·트랜잭션 재시도·체크포인트 검증은 추가다. 하루1만 문서 정리의 추가2읽기만 계산하면 월60만 읽기/$0.228(무료분 차감 전)이며, 실제 처리 시간 증가는 운영 검증 전 미확인이다.
- 앞 표의 월$3~10 예비비는 이런 부대 실행의 임시 준비액이며 위 비용에 다시 예비비를 중복 더한 확정 청구액이 아니다. 정리 적체·반복 장애·대량 신고에서는 이를 초과할 수 있다. 랭킹/서버 진행 검증은 여전히 제외다.

### 제한의 효과와 한계

계정별 분당 조회30/변경10, 신고 일5, 관리자/예약 동시성·배치 제한은 단일 계정/한 실행의 부하를 줄인다. **여러 계정을 만드는 남용과 프로젝트 전체 지출을 막는 월 상한은 아니다.** 거절 요청도 서버에 도착한 실행·DB 읽기에 비용이 생긴다.

maxInstances2는 사용자 함수6개의 합계2가 아니라 함수별2다. 예를 들어6개가각2개의1vCPU인스턴스를 한 달 내내 쓰는 모형은 CPU만 약$1,045(무료분 차감 전)로, 월20만원보다 크다. 이는 예측 청구액이 아니라 인스턴스 수 제한만으로 월 예산이 보장되지 않음을 보여주는 극단 예시다. 일시적 증가/다른 서비스 비용까지 완전 차단한다고 해석하지 않는다.

사용자가 선택한 네 알림은25%/50%/75%/100% 기준의 계획이다. 알림 지연과 누적 청구를 감안해야 하며 비용 도달 시 즉시 전체 서버가 멈추는 장치가 아니다. 서비스별 spend cap 도입 여부/저장·삭제 중단 영향은 별도 승인안으로 다루고 이번에 설정하지 않는다.

## 0.80.0 당시 1차 산식과 이력

아래는 0.80.0 작성 당시의 기본 수동 저장 산식과 검증 이력이다. 신고 읽기/쓰기 수, 정리 방식, 주기·알림 결정과 현재 준비 상태는 **위 0.81.0 절이 우선**한다. 당시 미확정·미검증이라는 문장을 현재 상태로 해석하지 않는다.

0.80.0 코드와 서울(asia-northeast3) 공식 단가로 만든 **사용량 시나리오**다. 실제 청구액이나 운영 측정 결과가 아니다. 사용자에게 예상 이용자 수를 아직 받지 않았으므로 규모별로 계산했다.

월 20만원은 사용자 지정 계획 기준이다. 이번 추정은 Blaze 전환, 예산 생성, 함수/예약 설정 변경 또는 배포 승인이 아니다. 1단계 콘솔 확인도 아직 남아 있다.

## 계산 가정

- 월 30일, 하루 한 사람당 서버 기록 확인 3번 + 서버 저장 3번. 기록 확인 1번은 프로필 조회와 저장 조회, 총 2함수 호출이다. 두 기기 사용은 같은 계정 사용량에 합산한다.
- 현재 호출 제한은 계정당 최근 60초 조회 30/변경 10회. 이는 허용 최대치이며 위 표의 평균 사용량 가정과 다르다. 게임 터치·모집·전투는 서버 호출을 하지 않는다.
- 2세대 Functions, 서울, 1vCPU/256MiB, 최소 상주 인스턴스 0을 가정. 코드에는 region과 함수별 maxInstances 2만 지정되어 있다. 실제 배포 설정은 아직 없으며 변경하지 않았다.
- 함수 호출당 독립 실행시간 0.3~1초를 가정했다. 실제 측정값이 아니다. 동시 처리의 CPU 공유 절감은 적용하지 않았고, 시작·재시도·느린 외부 인증의 추가 시간은 기본 산식 밖이다.
- 무료 할당량을 다른 프로젝트가 쓰지 않는 가정. Cloud Run의 CPU/RAM 무료분은 결제 계정 단위이며, 서울 초수에서 무료 초수를 직접 빼지 않고 Tier 1 단가의 달러 할인액을 뺀다.
- 한 저장 원문 20KiB 가정. 메모리에서 새로 만든 freshState의 serializeSave 결과는 2,350바이트였지만 성장한 기록의 평균값으로 삼지 않았다. 실제 이용자 기록은 열거나 전송하지 않았다. 하루 저장 원문 6회 전송(저장 조회 3회 + 저장 응답 3회), 압축 절감 없음. JSON 부가 필드·프로필 응답 등은 예비비에 포함.
- 누적 미탈퇴 계정 수를 하루 이용자의 3배라고 가정. 현재/직전/최초 기록 3개, 문서 메타데이터·색인 등을 원문의 추가 100%로 임시 반영했다. 장기 보관 계정이 늘면 DAU가 같아도 저장 비용은 늘어난다.
- 호출 집계 정리는 계정당 하루 최대 3번 정리되는 모형: 문서당 스캔 읽기 1 + 재확인 읽기 1 + 삭제 1. 이는 비용 가정이며 예약 주기 결정/적용이 아니다.
- 계정 등록·신고·삭제·삭제 재시도와 90일 정리, 예약 실행 CPU, 콜드스타트, 추가 전송, 빌드/이미지/로그 등의 미측정분에 월 $3~10을 임시 예비비로 더했다. 이 금액은 사용량 산출치나 상한 보장이 아니다. 운영 측정 후 교체한다.
- 일반 Google 로그인 사용, SMS 인증 없음. 현재 범위에서 별도 유료 Auth 기능을 전제로 하지 않았다.

## 코드에서 확인한 작업 수

정상 요청에는 UID 호출 제한 트랜잭션 1읽기+1쓰기, Admin Auth getUser 확인이 공통으로 들어간다.

| 기능 1회 | Firestore 읽기 | 쓰기 | 비고 |

| 프로필 조회 | 3 | 1 | 삭제 상태·프로필·호출 제한 |
| 저장 조회 | 3 | 1 | 삭제 상태·저장·호출 제한 |

따라서 기본 모형은 **1인/일 9함수 호출 + 30읽기 + 15쓰기**다. 관련 코드: server/request-security.js, server/profile-service.js, server/cloud-service.js, server/report-service.js. 트랜잭션 충돌·재시도와 실패 요청 비용은 별도로 늘 수 있다.

호출 제한으로 거절한 요청도 함수 실행·집계 조회 비용이 발생할 수 있다. App Check 거절과 maxInstances는 월 지출의 완전한 차단 장치가 아니다.

## 20만원을 넘을 수 있는 조건과 다음 확인

- 이용자 수뿐 아니라 서버 버튼 횟수, 실행시간, 저장 크기, 무료분 공유, 실패/재시도가 중요하다. 호출이 10배 늘면 소규모 이용자라도 표의 상위 규모와 비슷해진다. 호출 제한을 정상 사용량 예상으로 삼지 않는다.
- 랭킹 계산/조회/갱신, 서버가 게임 진행을 계산하는 검증은 미구현이므로 이번 표에서 제외했다. 3단계 설계 시 합산하고 사용자에게 다시 보고한다.
- Play Integrity 10,000회/일은 이용자 수나 함수 호출 수와 같은 수치가 아니다. 토큰 재사용/세션 갱신을 확인하고, 규모 확대 전 할당량을 검토한다.
- minInstances 상향은 대기 비용을 만들 수 있다. maxInstances 2는 함수별 제한이어서 6개 함수 합계 2개라는 뜻이 아니다.
- 예산 알림은 지출을 막지 않는다. Google의 서비스별 spend cap은 일부 서비스에 적용되며 Firestore까지 전체 합계 20만원을 보장하는 장치로 간주하지 않는다. 지원 범위/초과 가능성/중단 후 저장·삭제 영향은 [공식 문서](https://docs.cloud.google.com/billing/docs/how-to/budgets-spend-caps)를 기준으로 배포 승인 전에 구체화한다. 이번에는 생성하지 않았다.
- 0.80 작성 당시에는 삭제 재처리 주기·배치량·최대 실행시간·알림 금액이 미확정이었다. 0.81에서 사용자 결정과 코드 후보를 상단에 정리했지만 실제 적용은 하지 않았다. 배포 이미지 정리·로그 보관의 운영 설정은 별도 승인안에 비용과 기능 영향을 포함한다.
- 사용자 승인과 1단계 잔여 확인 후에만 테스트 전용 계정으로 실제 응답시간·전송량·청구 지표를 확인한다. 현재 운영 배포/실제 로그인/실기기/Node22 동등성은 미완료다.
