# 닉네임 금칙어·신고 처리 초안

사용자 선택 범위: **운영자 사칭 + 심한 욕설·혐오·성적 표현·개인정보 노출**. 아래는 이 범위의 첫 구현 목록이며 출시 확정 문안이나 완전한 자동 판별을 뜻하지 않는다. 실제 운영 배포·신고 접수·제재는 아직 수행하지 않았다. 금칙어 예시는 자동 검증 기준을 검토하기 위한 것이다.

## 1. 서버 등록 검사

닉네임은 기존 규칙대로 글자·숫자·밑줄 2~12자, NFKC 정규화·대소문자 구분 없는 고유 이름이다. 변경권·무료 변경 횟수는 정하지 않았다. 금칙어 검사는 서버에서 실행하며 앱 화면 검사를 우회해도 적용된다.

금칙어 비교 때만 밑줄을 제거한다. 따라서 `운영_자`, `game_master`, 전각 `ＡＤＭＩＮ`도 차단한다. 중복 판정용 이름에서는 밑줄을 그대로 유지하므로 기존 닉네임 소유권을 바꾸지 않는다.

| 범위 | 이번 코드의 목록·규칙 |
| --- | --- |
| 운영자 사칭 | 운영자, 관리자, 동람코, admin, moderator, gamemaster, dongramco 포함. `gm` 또는 `gm` 뒤 숫자만 있는 이름도 차단 |
| 심한 욕설 | 씨발, 씨빨, 개새끼, 씹새끼, 병신, 좆, motherfucker, fuck, cunt 포함 |
| 혐오 표현 | 한남충, 한녀충, 김치녀, 맘충, 짱깨, 깜둥이, nigger 포함 |
| 성적 표현 | 강간, 성폭행, 포르노, 섹스, 야동 포함 |
| 개인정보 형태 | 국내 휴대전화·지역 전화번호 형태 및 82로 시작하는 휴대전화 형태. 이메일의 `@`·주소 구분자와 URL 구분자는 기존 문자 규칙에서 거부 |

전화번호 형태는 공개 시험용 숫자로만 시험했다. 특정인의 실제 전화번호를 수집·대조하지 않는다. 이름의 일부가 우연히 목록과 일치하거나 긴 숫자가 전화번호처럼 보이면 차단될 수 있다. 영어 `gm`을 일반 부분 문자열로 막지 않으며 `sigmar`, `grape` 같은 정상 예시는 허용하는 회귀 검사를 둔다.

### 2026-10-12 A3 보완 — 부분 일치 오탐과 우회 사례

실제로 `Badminton`의 `admin`, `Scunthorpe`의 `cunt`가 차단되는 오탐을 재현했다. 이 두 정상 영어 단어에 들어 있는 해당 조각만 좁게 예외 처리한다. 대소문자·전각 정규화 후 **연속된 영문자 단어가 정확히 `badminton` 또는 `scunthorpe`일 때만** 적용한다. 숫자·밑줄로 구분된 `Badminton_1`, `scunthorpe12`, `Scunthorpe_x`도 허용하지만, 단어 안을 쪼갠 `bad_minton`, `s_cunthorpe`나 문자를 붙인 `xbadminton`, `scunthorpex`는 예외가 아니다. 다른 일반 단어까지 자동 승인하는 사전이나 닉네임 전체 검사 면제 목록은 넣지 않았다.

같은 이름의 다른 금칙어는 계속 검사한다. 예를 들어 `Badminton씨발`, `Scunthorpe좆`, `Badminton관리자`는 차단된다. 예외는 등록 검사 비교에만 쓰며 닉네임 고유 키·대소문자/밑줄 중복 판정·기존 닉네임 소유권은 바꾸지 않는다. 정상 이름 회귀 목록과 우회/한계 예시는 `tests/nickname-moderation.test.js`에 합성 입력으로 고정했다.

| 시험 종류 | 합성 예시 | 현재 결과와 한계 |
| --- | --- | --- |
| 밑줄·전각·대소문자 | `씨_발`, `F_u_C_k`, `ＦＵＣＫ`, `ad_min` | 원래 금칙어 조각으로 정규화되어 차단 |
| 정규 한글 자모 분해 | `씨발` | NFKC로 `씨발`이 되어 차단 |
| 호환 자모 분리 | `ㅆㅣㅂㅏㄹ` | NFKC가 완성형 욕설로 모두 합쳐 주지는 않으므로 현재 누락. 별도 검토 필요 |
| 반복 문자 | `fuckkk`, `adminnn` / `fuuuck`, `씨이발` | 금칙어 원형이 남은 앞의 두 예시는 차단. 원형 중간이 늘어난 뒤의 두 예시는 현재 누락 |
| 비슷하게 보이는 다른 문자 | `fυck`의 그리스 문자 `υ`, `admіn`의 키릴 문자 `і` | 전각 영문과 달리 ASCII로 바뀌지 않아 현재 누락 |

**한계:** 은어·철자 변형·초성·다른 언어·시각적으로 비슷한 문자·실명/주소의 문맥까지 완전히 알아내지 못한다. 누락 예시의 테스트는 현재 자동 판별 범위를 드러내기 위한 것이며 그 이름을 적절하다고 승인하는 기준이 아니다. 자모/반복/유사문자를 모두 합치는 규칙은 정상 이름까지 막을 수 있으므로 이번 오탐 보완에 임의로 추가하지 않았다. 현재 목록을 통과했다고 모든 닉네임이 적절하다고 보장하지 않는다. 기존에 등록된 이름을 목록 수정만으로 자동 삭제하거나 계정을 정지하지 않는다. 발견된 기존 이름은 신고 후 운영자가 검토한다. 목록의 오탐·누락 수정은 검토 기록을 남기는 별도 변경이며 사용자 전체 저장을 수정하지 않는다. 이번 절의 수정은 금칙 범위나 새로운 수집 정보·신고 보관 기간·제재 절차를 정하지 않는다.

## 2. 신고 API와 보관 정보 — 0.81.0 준비 기준

아래 수치와 처리 방식은 사용자 설문에서 승인받았다. 코드와 로컬 검증을 준비한 상태이며, 운영 서버에 배포하거나 실제 신고를 접수·처리하지는 않았다.

- 로그인 후 자신의 닉네임을 등록한 계정이 앱의 **닉네임 신고** 화면에서 대상 닉네임과 사유를 선택한다.
- 사유는 impersonation, abuse, hate, sexual, personal-info 다섯 값만 받는다. 자유문장·증거 파일·이메일·전화번호 입력칸은 없다.
- 서버가 인증한 신고자 UID를 사용하고, 대상 닉네임의 현재 소유 UID와 닉네임 변경 세대를 서버에서 찾는다. 클라이언트가 보낸 신고자·대상 UID, 일일 집계 값, 변경 세대는 사용하지 않는다.
- 대상이 없는 이름, 자기 신고, 닉네임이 없는 신고자, 삭제 중인 신고자·대상은 거부한다. 이미 금칙어에 걸리는 기존 이름도 신고할 수 있도록 조회용 정규화와 신규 등록 검사를 구분한다.
- 신고자별 **한국 시간 하루 5건**까지 새 신고를 접수한다. 한국 시간 자정에 새 일일 한도가 시작된다. 계정별 최근 60초 변경 10회 제한도 함께 적용하며, 두 기기에서 요청해도 한 계정의 한도로 합산한다.
- 같은 신고자·대상 UID·닉네임 변경 세대와 고유 이름에는 **사유와 무관하게 1회**만 접수한다. 같은 신고의 재전송은 새 건수로 세지 않으며 처리 상태도 초기화하지 않는다. 이름이 변경된 뒤에는 새 세대의 이름을 다시 신고할 수 있다.
- 응답은 {submitted:true}뿐이다. 신고자 정보, 대상 UID, 신고 문서 ID, 처리 상태를 다른 이용자에게 반환하지 않는다. Firestore 직접 읽기·쓰기는 계속 거부한다.

### 자료별 내용과 보관 기준

| 자료 | 저장하는 내용 | 보관·정리 기준 |
| --- | --- | --- |
| nicknameReports | 신고자·대상 UID, 접수 당시 이름과 변경 세대, 사유, 접수 시각, 상태. 처리 시 버전·조치 연결·완료/만료 시각 등 추가 | 미처리는 검토 완료까지, 처리한 원문은 완료 후 90일 |
| reportDedup | 신고자·대상 UID, 닉네임 변경 세대, 고유 이름의 해시. 이름 원문·사유·처리 상태는 없음 | 원문 삭제 후에도 중복 방지를 위해 유지. 대상의 닉네임 변경 또는 양쪽 계정 중 한 계정의 탈퇴 시 삭제 |
| reportDaily/{신고자 UID} | 한국 시간 날짜, 접수 건수, 만료 시각 | 다음 한국 시간 자정에 만료하며, 새 날짜 집계로 교체하거나 만료 정리 작업으로 삭제 |
| moderationActions | 조치·복원 ID와 신고 연결, 당사자 연결, 관리자 해시, 변경 전후의 최소 이름·안내·변경 번호, 처리 시각 등 | 각 처리·복원 완료 후 90일 |
| moderationCleanup | 실패한 이전 세대 정리를 위한 당사자 연결, 이전 세대, 작업 시각. 이름 원문·신고 사유는 없음 | 정리 성공 시 삭제. 미완료 작업은 성공할 때까지 재시도하며, 관련 계정 탈퇴 시 함께 삭제 |

신고와 중복 방지 문서 ID는 [신고자 UID, 대상 UID, 닉네임 변경 세대, 고유 이름] 배열을 JSON으로 직렬화한 값의 SHA-256이다. 고유 이름의 별도 해시도 같은 직렬화 기준을 사용한다. 닉네임 변경 세대가 없는 기존 프로필은 0으로 읽는다. 해시로 바꾸었다고 이 자료가 익명 정보가 되는 것은 아니며, 서버 접근 제한과 위 보관 기준을 그대로 적용한다.

이전 미배포 초안은 신고자·대상·사유별 문서 ID를 사용했다. 새 코드는 최초 이름 세대에서 해당 구형 문서를 확인하여 기존 처리 상태를 보존하고 최소 중복 방지 정보를 보강한다. 기존 환경에 구형 자료가 실제로 있다면 원문 만료 정리를 켜기 전에 전체 자료의 중복 방지 정보 보강을 확인해야 한다. 요청 시점의 호환 조회만으로 이미 지워진 구형 원문을 복구할 수는 없다. 실제 사용자 자료의 이관은 이번 작업에서 수행하지 않았다.

삭제 완료 확인 기록의 90일과 신고·처리 기록의 90일은 서로 다른 자료의 보관 기준이다. 기간이 같다는 이유로 미처리 신고, 중복 방지 값, 실패한 정리 작업을 한꺼번에 지우지 않는다.

## 3. 계정 탈퇴와 연동

신고자 또는 대상이 탈퇴하면 해당 UID가 reporterUid 또는 targetUid인 nicknameReports, reportDedup, moderationActions, moderationCleanup 자료를 삭제한다. 탈퇴 계정의 reportDaily 집계와 rateLimits 호출 제한 기록도 삭제한다. 양쪽 UID 조회가 같은 문서를 가리키더라도 안전하게 처리하며, 관련 이름이나 식별자를 별도 익명 통계로 복사하지 않는다.

신고·관리 조치 트랜잭션은 양쪽 계정의 삭제 표식을 읽는다. 삭제와 접수가 충돌하면 트랜잭션 재시도에서 거부한다. 삭제 작업은 표식을 먼저 남기고 관련 자료를 정리한 뒤 완료로 표시한다. 일부 자료 정리가 실패하거나 한 번에 처리할 수 있는 양을 넘으면 미완료로 남겨 재시도한다. 실패 중 요청을 보관 기간 만료로 지우지 않는다.

삭제 재시도는 6시간마다, 만료 자료 정리는 하루 1번 실행하도록 **코드만 준비**했다. 실제 예약 설정·서버 배포·운영 삭제 검증은 미완료다.

## 4. 운영 처리 순서 — 코드 준비, 실운영 미검증

1. **운영자 본인만** 인증된 비공개 관리자 경로에서 미처리 신고를 확인한다. 로컬 관리자 도구는 목록·상세·처리·복원 기능을 제공한다. 사용자 앱에는 관리 버튼이나 승인·제재 callable을 노출하지 않는다.
2. 신고 당시와 현재의 닉네임·변경 세대가 같은지, 승인된 금칙 범위에 해당하는지 검토한다. 신고 횟수만으로 판단하지 않는다. 해당하지 않는 신고는 기각한다.
3. 필요한 조치는 **경고 또는 서버가 중복 확인한 기본 닉네임 부여**다. 자동 정지, 랭킹 제외, 게임 저장 삭제를 실행하지 않는다. 일반 닉네임 변경권과 무료 변경 횟수는 여전히 미정이다.
4. 처리 전 미리보기를 확인하고 실행한다. 상태는 pending에서 resolved 또는 dismissed로 바뀌며 처리 기록을 남긴다. 응답이 불명확하면 같은 조치 ID로 재시도한다.
5. 오조치 복원은 이후 다른 조치가 없고 현재 상태와 이름 소유권이 예상과 일치할 때만 실행한다. 기존 이름을 다른 계정이 소유하면 덮어쓰지 않는다. 복원한 신고는 다시 pending이 되며, 이름을 되돌렸더라도 닉네임 변경 세대는 증가한다.
6. 이용자는 다음 프로필 조회에서 조치 안내와 기존 앱 문의 이메일을 확인한다. 이의제기는 해당 이메일로 받는다. 실제 접수·본인 확인·회신 절차는 운영 검증이 필요하며, 코드 준비만으로 운영 중이라고 표시하지 않는다.
7. 오탐이나 누락이 발견되면 승인된 금칙 범위 안에서 목록을 검토한다. 실제 이름·UID·토큰을 공개 작업일지에 쓰지 않는다.

관리자 권한 최소화, 2단계 인증, 계정 복구와 재시도 절차는 [닉네임 운영 도구 준비안](MODERATION_OPERATIONS.md)을 따른다. 실제 IAM·관리자 인증은 아직 확인하지 않았다.

## 5. 검증 범위와 정책 반영

합성 데이터로 금칙어 오탐과 우회 한계, 인증·자기 신고·대상 없음·삭제 중 거부, 일일 한도와 한국 시간 자정 경계, 중복 접수, UID·변경 세대 위조 무시, 최소 보관 정보, 계정 전환 중 늦은 응답 무시, 오류 정제와 화면 이스케이프를 검사한다.

관리자 처리·복원, 무권한 호출 거부, 닉네임 소유권 충돌, 부분 정리 실패와 관련 자료 삭제도 검증 대상이다. 실제 통과한 테스트 수와 빌드·에뮬레이터 결과는 [검증결과](../검증결과.md)의 0.81.0 기록을 기준으로 한다. 이 문서는 실제 Functions 배포·Google 로그인·운영 신고 처리·실기기 검증을 대신하지 않는다.

신고·처리·중복 방지 자료의 수집 필드, 목적, 관리자 접근, 보관·삭제, 이의제기 경로를 앱 방침·스토어 문서·공개 방침·Play 데이터 보안 양식에 맞춰야 한다. 최종 문안 승인 전에는 방침 11·약관 8 번호를 올리지 않는다. **정책 동기화 필요.**
