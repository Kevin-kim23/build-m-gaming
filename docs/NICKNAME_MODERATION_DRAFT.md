# 닉네임 금칙어·신고 처리 초안

사용자 선택 범위: **운영자 사칭 + 심한 욕설·혐오·성적 표현·개인정보 노출**. 아래는 이 범위의 첫 구현 목록이며 출시 확정 문안이나 완전한 자동 판별을 뜻하지 않는다. 실제 운영 배포·신고 접수·제재는 아직 수행하지 않았다. 금칙어 예시는 자동 검증 기준을 검토하기 위한 것이다.

## 1. 서버 등록 검사

닉네임은 기존 규칙대로 글자·숫자·밑줄 2~12자, NFKC 정규화·대소문자 구분 없는 고유 이름이다. 변경권·무료 변경 횟수는 정하지 않았다. 금칙어 검사는 서버에서 실행하며 앱 화면 검사를 우회해도 적용된다.

금칙어 비교 때만 밑줄을 제거한다. 따라서 `운영_자`, `game_master`, 전각 `ＡＤＭＩＮ`도 차단한다. 중복 판정용 이름에서는 밑줄을 그대로 유지하므로 기존 닉네임 소유권을 바꾸지 않는다.

| 범위 | 이번 코드의 목록·규칙 |
| --- | --- |
| 운영자 사칭 | 운영자, 관리자, 동람코, admin, moderator, gamemaster, dongramco 포함. `gm` 또는 `gm` 뒤 숫자만 있는 이름도 차단 |
| 심한 욕설 | 씨발, 씨빨, 개새끼, 씹새끼, 병신, 좆, motherfucker, fuck, cunt 포함 |
| 혐오 표현 | 한남충, 한녀충, 김치녀, 맘충, 짱깨, 깜둥이, nigger 포함 |
| 성적 표현 | 강간, 성폭행, 포르노, 섹스, 야동 포함 |
| 개인정보 형태 | 국내 휴대전화·지역 전화번호 형태 및 82로 시작하는 휴대전화 형태. 이메일의 `@`·주소 구분자와 URL 구분자는 기존 문자 규칙에서 거부 |

전화번호 형태는 공개 시험용 숫자로만 시험했다. 특정인의 실제 전화번호를 수집·대조하지 않는다. 이름의 일부가 우연히 목록과 일치하거나 긴 숫자가 전화번호처럼 보이면 차단될 수 있다. 영어 `gm`을 일반 부분 문자열로 막지 않으며 `sigmar`, `grape` 같은 정상 예시는 허용하는 회귀 검사를 둔다.

**한계:** 은어·철자 변형·초성·다른 언어·시각적으로 비슷한 문자·실명/주소의 문맥까지 완전히 알아내지 못한다. 현재 목록을 통과했다고 모든 닉네임이 적절하다고 보장하지 않는다. 기존에 등록된 이름을 목록 수정만으로 자동 삭제하거나 계정을 정지하지 않는다. 발견된 기존 이름은 신고 후 운영자가 검토한다. 목록의 오탐·누락 수정은 검토 기록을 남기는 별도 변경이며 사용자 전체 저장을 수정하지 않는다.

## 2. 신고 API와 보관 정보

- 로그인 후 자신의 닉네임을 등록한 계정이 앱의 **닉네임 신고** 화면에서 대상 닉네임과 사유를 직접 선택한다.
- 사유는 `impersonation`, `abuse`, `hate`, `sexual`, `personal-info` 다섯 값만 받는다. 자유문장·증거 파일·이메일·전화번호 입력칸은 없다.
- 서버가 인증한 신고자의 UID를 사용하고 대상 닉네임의 현재 소유 UID를 서버에서 찾는다. 클라이언트가 보낸 신고자/대상 UID는 사용하지 않는다.
- 대상 없는 이름, 자기신고, 닉네임이 없는 신고자, 삭제 진행 중인 신고자 또는 대상은 거부한다. 이미 금칙어에 걸리는 기존 이름도 신고할 수 있도록 조회용 정규화와 신규 등록 검사를 구분한다.
- `nicknameReports/{sha256([reporterUid,targetUid,reason])}`에 신고자 UID·대상 UID·접수 당시 대상 닉네임·사유·접수 시각·상태를 보관한다. 최초 상태는 `pending`. 같은 신고자·대상·사유는 재전송해도 한 건이며 기존 처리 상태를 초기화하지 않는다.
- 클라이언트 응답은 `{submitted:true}`뿐이다. 신고자 정보·대상 UID·신고 문서 ID·처리 상태를 다른 이용자에게 반환하지 않는다. Firestore 직접 읽기/쓰기는 기존 거부 규칙을 유지한다.
- 신고도 사용자 확정 계정별 변경 호출 한도에 포함한다. 호출 제한 수치는 공통 서버 설정을 따르고 이 모듈이 별도 횟수를 정하지 않는다.
- **신고 자체의 보관 기간은 아직 미정**이다. 삭제 완료 확인 기록 90일과 신고 보관 기간은 다른 항목이므로 자동으로 90일을 적용하지 않는다. 운영 시작 전에 처리 목적·보관/파기 기간을 확정하고 방침과 정리 작업에 반영해야 한다.

## 3. 계정 탈퇴와 연동

신고자 또는 대상이 탈퇴하면 그 UID가 `reporterUid` 또는 `targetUid`인 신고 문서를 모두 삭제한다. 두 쿼리는 같은 문서를 가리킬 수 있으므로 중복 삭제는 안전하게 처리한다. 관련 이름·신고자 식별자를 별도 익명 통계라고 복사하지 않는다.

신고 트랜잭션은 양쪽 계정의 삭제 표식을 읽는다. 삭제 표식 생성과 신고 접수가 충돌하면 트랜잭션 재시도 때 접수를 거부한다. 삭제 작업은 표식을 먼저 남기고, 관련 신고를 모두 지운 뒤 삭제 완료로 표시해야 한다. 실패하면 미완료로 유지하고 재시도한다. 신고 하위 컬렉션을 몰래 남기는 구조는 사용하지 않는다.

## 4. 운영 처리 순서 — 아직 실운영 미검증

1. 권한 있는 운영자만 비공개 서버 관리 경로로 미처리 신고를 확인한다. 인증 토큰·이메일·전체 게임 저장을 신고 검토 화면이나 작업일지에 복사하지 않는다. 현재 전용 운영자 화면은 없다.
2. 신고된 이름이 실제 현재 닉네임과 같은지, 사용자가 선택한 금칙어 범위에 해당하는지 검토한다. 신고 횟수만으로 판단하지 않는다. 허위·중복·해당 없음이면 제재하지 않는다.
3. 제재 종류·기간, 강제 닉네임 변경 방법 및 이의제기 절차는 아직 확정하지 않았다. 닉네임 변경권 결정과도 분리한다. 운영자 검토 없이 자동 정지·랭킹 제외·저장 삭제를 실행하지 않는다. 출시 전에 운영자가 실제 사용할 조치 경로와 이의제기 안내를 정해야 한다.
4. 처리 상태만 비공개 문서에 남기며 원문 자유 메모·새 개인정보는 추가하지 않는다. 현재 API는 접수 전용이므로 관리자 처리 도구·권한·오조치 복원 검증이 별도로 필요하다.
5. 오탐 신고를 받으면 승인된 범위를 기준으로 목록을 검토한다. 새 범위나 새로운 개인정보 보관을 임의로 추가하지 않는다. 공개 작업일지에는 실제 닉네임·UID를 쓰지 않는다.

## 5. 검증 범위와 정책 반영

금칙어 우회·정상 이름 오탐 예시, 인증/자기신고/대상 없음/삭제 중 거부, 중복 접수, UID 위조 무시, 개인정보 최소 저장, 계정 전환 중 늦은 응답 무시, 오류 정보 정제와 UI 이스케이프를 합성 데이터로 검사한다. 이는 실제 Functions 배포·실제 계정 로그인·실제 신고 처리·실기기 검증을 대신하지 않는다.

닉네임 신고 처리는 추가 서버 수집이므로 앱 방침·스토어 문서·공개 방침·Play 데이터 보안 양식에 수집 필드, 목적, 운영자 접근, 보관/삭제 및 이의제기 경로를 맞춰야 한다. 최종 문안 확정 전에는 방침11·약관8 번호를 올리지 않는다. **정책 동기화 필요.**
