# 월 10만 원 비용 보호 · 0.82.0 · 2026-10-13

> 후속 진행: 관리자 계정 파트A의 콘솔 설정은 완료했다([실제 검증](STAGE3_ADMIN_COST_PREPARATION.md)). 게임 함수/비용 보호 배포는 아직 하지 않았다. 운영 한도 미정·파트B 코딩 보류·운영 콘솔 금지는 유지한다. 아래 이름만 승인 상태는 이전 기록이다.

> 3단계 최신: [관리자 계정·운영 준비 인계](STAGE3_ADMIN_COST_PREPARATION.md). 운영도 별도 월 한도로 중단/복구할 방향은 승인됐으나 **운영 금액 미정, 운영용 코딩 보류**다. 현재 구현은 개발 전용이며 아래 운영 범위 설명은 현행 구현 기준이다. 운영 콘솔·배포 금지. 관리자 계정 이름만 승인됐고 비용 보호 계정/Pub/Sub는 게임 함수9개와 예약 작업2개 배포 뒤에 만든다. 이번 단계 콘솔 재확인은 하지 않았다.

**현재는 코드 준비다. 실제 자동 중단은 아직 꺼져 있다.** 사용자는 개발 프로젝트의 Blaze 전환을 알렸고 Chrome에서 Blaze·KRW·월 100,000원 예산과 50/90/100% 알림, 자동 중단 없음까지 읽기 확인했다. 이번에는 콘솔·IAM·배포를 변경하지 않았다. 기존 월 20만 원 계획보다 이번 결정이 우선한다.

## 확정 범위와 한계

- 기준: `budae-kiugi-dev` 프로젝트의 **모든 서비스 합산**, 월 예산 보고 비용 **100,000원 이상**. 원화·월간·프로젝트 1개·모든 서비스·모든 크레딧 반영을 검증한다. 실제 청구서의 세금·지연 정산을 포함한 결제액과 다를 수 있다.
- 운영 프로젝트나 다른 프로젝트의 비용은 현재 예산에 포함되지 않는다. 나중에 운영을 시작할 때 개발+운영 총예산의 범위와 중단 대상을 함께 다시 설계해야 한다. 프로젝트마다 10만원씩 주어 전체 20만원으로 늘리지 않는다.
- 중단 대상: 게임 함수 9개에 연결된 Cloud Run 서비스와 게임 예약 2개. DB·Auth 계정·저장·신고·삭제 대기 기록은 지우지 않는다. 클라이언트의 Firestore 직접 접근은 기존 규칙으로 거부한다.
- 자동화 자체는 별도 함수로 계속 동작한다. 데이터/백업/빌드 이미지 보관, 예약 리소스, 자동화·알림 등의 비용은 남을 수 있다. 새 서비스를 추가하면 이 자동화의 대상과 예산 범위도 검토해야 한다. 모든 Google 비용의 결제 차단 기능은 아니다.
- 비용 통지는 실시간이 아니다. 하루 여러 차례 전달되고 처음 연결 후 수 시간이 걸릴 수 있다. 이미 처리 중인 요청은 완료될 수 있다. **정확히 10만원에서 결제가 멈춘다는 보장은 없으며 초과 청구될 수 있다.** 위험을 더 줄이려면 별도 합의로 중단 기준을 낮춰야 한다. 이번에는 임의로 낮추지 않았다.
- 다음 달의 최신 비용 통지에서 10만원 미만을 확인하면 원래 설정으로 복구한다. 청구 기간은 Pacific 기준이며 한국 시간 1일 0시에 즉시 재개되는 것이 아니다. 다음 달도 이미 한도를 넘었거나 설정 충돌/권한 실패가 있으면 자동 재개하지 않는다.

## 코드 동작

`cost-control/`은 독립 Node 22 패키지다. `firebase.cost-control.json`으로만 별도 배포한다. 평소 게임 배포에 섞지 않았고 APK/AAB에는 포함되지 않는다. 기존 서버 패키지와 동일한 firebase-admin 14.5.0(Apache-2.0), firebase-functions 7.4.0(MIT), google-auth-library 11.2.0(Apache-2.0)을 사용하며 새로운 앱 SDK·Android 권한은 추가하지 않았다.

1. 비공개 Pub/Sub 예산 통지 → 예산 ID·결제계정·원화·실제 비용·월을 검증한다. 예상 비용만으로 중단하지 않는다. 예산 API도 읽어서 다른 프로젝트·서비스 일부만 집계하는 설정을 거부한다.
2. `observe` 모드는 예산과 실제 대상 11개의 읽기 권한·상태만 점검한다. `enforce`에서만 변경한다. 기본 설정 예시는 observe다.
3. Firestore `costControl/monthlyBudget`에 잠금과 원래 실행 설정을 먼저 기록한다. 게임 저장과 분리되며 직접 클라이언트 접근은 불가하다. 동시 실행은 막고 중복 통지는 멱등 처리한다.
4. 예약을 먼저 일시정지하고 각 함수의 **실제 Cloud Run 서비스**를 확인해 수동 인스턴스 0으로 바꾼다. 이미지·권한·환경변수·최대 인스턴스 설정은 바꾸지 않는다. 트래픽 태그가 있으면 태그 전용 리비전이 계속 동작할 수 있어 해당 대상을 오류로 기록한다.
5. 부분 실패는 다른 대상의 중단까지 막지 않는다. 다음 비용 통지에서 다시 상태를 확인한다. 실패를 무한 즉시 재전송하지 않고 오류 알림을 운영자가 확인한다. API 요청·처리 시간·인스턴스를 제한한다.
6. 같은 달에 비용이 낮게 정정되어도 중단 상태를 유지한다. 오래된 통지로 다음 달을 다시 중단하거나, 오래된 낮은 비용으로 재개하지 않는다.
7. 재개 시 서비스부터 복구하고 그다음 예약을 복구한다. 원래 수동으로 멈춰 있던 예약은 켜지 않는다. 운영자가 새 리비전을 배포하거나 설정을 변경하면 덮어쓰지 않고 재검토를 요구한다.

## 다음 PC에서 실제 연결하는 순서

이 저장소 규칙상 **콘솔 변경은 사용자가 직접 한다.** 한 번에 하나씩 안내한다. 운영 프로젝트는 이번 승인 범위가 아니다. 이 문서를 읽었다고 운영 배포나 main 병합이 허용되는 것은 아니다.

1. 기존 [서버 배포 순서서](SERVER_DEPLOYMENT_RUNBOOK.md)에 따라 승인된 개발 게임 함수 9개와 예약 2개가 준비되어 있어야 한다. 미배포 상태에서는 자동화 대상 검증을 통과할 수 없다. 관리자 함수의 별도 실행 계정 조건도 유지한다.
2. 전용 실행 계정 `budget-cost-guard@budae-kiugi-dev.iam.gserviceaccount.com`을 만든다. 키 파일은 만들지 않는다. 실제 대상 리소스와 IAM 조건을 확인한 후 최소 권한으로 부여한다. 게임/앱 계정에 이 권한을 주지 않는다.
3. 개발 프로젝트에 `budae-budget-events` Pub/Sub 주제를 만든다. 공식 예산 연결 절차는 작업자의 주제 `pubsub.topics.setIamPolicy` 권한이 필요하다. 연결 과정에서 부여되는 Google Cloud Billing 발행 권한을 실제 IAM 화면에서 확인한다. 발행자 계정명을 추측해서 등록하지 않는다. 앱·일반 사용자·allUsers에는 발행/함수 호출 권한을 주지 않는다. 발행자는 이벤트 안 필드만 검사해서 확인할 수 없으므로 **주제 IAM이 보안 경계**다.
4. 현재 월 100,000원 예산에 이 주제를 연결하고 schema 1.0, 프로젝트/서비스/크레딧 필터를 확인한다. 기존 50/90/100% 이메일 알림은 유지한다. 실제 결제계정·예산 ID는 공개 Git/채팅에 남기지 않는다.
5. `cost-control/.env.example`을 로컬 `.env.budae-kiugi-dev`로 복사하고 실제 식별자를 채운다. Git 제외 대상이다. 처음에는 `COST_GUARD_MODE=observe`를 유지한다.
6. 배포 전 해당 명령의 환경변수 `GCLOUD_PROJECT=budae-kiugi-dev`를 지정하고 `node tools/check-cost-control.mjs` 오프라인 검사, `node tools/inspect-cost-control.mjs` 실제 읽기 전용 검사를 한다. 후자는 로컬 Application Default Credentials가 필요하다. 인증 토큰을 출력하거나 Git에 저장하지 않는다. 읽기 검사가 통과해도 실행 계정의 쓰기 권한 검증은 별개다.
7. 별도 설정으로 `budgetCostGuard`만 개발에 배포한다. 명령 대상은 `--config firebase.cost-control.json --project budae-kiugi-dev --only functions:cost-control:budgetCostGuard`다. CLI가 게임 함수 삭제/변경을 제안하면 중단한다. 실제 Pub/Sub 통지가 도착하고 해당 실행 계정에서 `observe` 및 전체 대상 읽기가 통과하는지 확인한다.
8. **실제 사용자 기록이 없는 개발 환경에서만** 중단·재개 리허설을 진행한다. 통지 발행 권한은 운영자에게 임시 최소 부여 후 회수한다. 예산 도달 합성 통지는 월 중단 상태를 남기므로, 실제 월초가 아닌 재개 검증은 아래 수동 복구 절차로 한다. 운영 예산/운영 주제로 합성 초과 이벤트를 보내지 않는다.
9. 9개 서비스 중단·예약 2개 정지·503 확인·기기 기록 유지·DB 원본 보존·복구 후 요청 성공을 모두 확인한다. 그 결과와 권한 범위를 사용자에게 보여준 뒤 enforce로 전환한다. **이 단계 전에는 자동 중단 활성화 완료라고 보고하지 않는다.**

## 필요한 권한 검토표

실제 콘솔에서 리소스별 부여 가능 여부를 확인한다. 프로젝트 Owner/Editor를 이 함수의 실행 계정에 주지 않는다. 아래는 권한 후보이며 실제 검증 완료가 아니다.

| 범위 | 실행 계정에 필요한 동작 |
| --- | --- |
| 지정 예산의 결제 계정 | `billing.budgets.get` 읽기만 (지원 범위 내 별도 역할) |
| 개발 함수 9개 | `cloudfunctions.functions.get` |
| 대응 Cloud Run 서비스 9개 | `run.services.get`, `run.services.update`; 작업 상태 조회 `run.operations.get` |
| 해당 서비스 실행 계정 | Cloud Run 변경이 요구하는 `iam.serviceAccounts.actAs`만 검토 |
| 개발 Scheduler | `cloudscheduler.jobs.list`, 대상 예약의 `get/pause/enable` 검토(resume API 권한은 `cloudscheduler.jobs.enable`) |
| 개발 Firestore | 내부 상태 문서 트랜잭션을 위한 데이터 접근. Admin SDK는 보안 규칙을 우회하므로 IAM 권한이 게임 기록 전체에 미치는 범위도 검토한다. 앱 계정에는 부여하지 않는다. |
| 자동화 실행/전송 | 공식 Functions/Eventarc 배포 절차가 요구하는 서비스 에이전트·이벤트 전송 역할, 로그 기록. 일반 공개 HTTP 호출 권한 금지. |

배포자는 위 실행 계정으로 배포할 권한과 별도의 빌드 권한이 필요하다. 실행 계정에 예산 변경·결제 해제·DB 삭제·프로젝트 삭제 권한을 주지 않는다. 새 권한을 무조건 넓히기보다 실패한 API와 필요한 동작을 먼저 확인한다.

## 운영·중단 중 개인정보 요청·수동 복구

- `cost-control.resource` / `cost-control.notification` ERROR 로그와 통지 미수신을 감시하는 Cloud Monitoring 알림을 **실제로 연결**한다. 코드 준비만으로 운영자 알림이 발송되지는 않는다. 로그 원문에는 예산 ID·토큰·사용자 저장을 남기지 않는다. 이벤트 재시도는 꺼져 있으므로 다음 주기까지 기다리기 어려운 오류는 수동 대응한다.
- 중단 중 서버 저장·복원·신고·삭제 API와 예약 정리는 이용할 수 없다. 로그인 서비스 자체는 중단하지 않는다. 앱의 실패 안내는 기기 기록을 유지하고 저장 성공을 표시하지 않는다. 재개 뒤 이용자가 서버 저장을 다시 시도해야 한다. 아직 랭킹 기능은 구현 전이다.
- 개인정보 삭제 요청 접수와 만료 보관 기간 검토를 월말까지 미루지 않는다. 앱에서 접수할 수 없는 동안 문의 이메일로 요청을 받고, 권한 있는 운영자가 최소 범위로 수동 삭제/정리를 수행하는 절차를 실제 출시 전에 검증해야 한다. 수동 정리 비용도 발생할 수 있다. 기존 24시간 미처리 검토 기준을 유지한다. 이 문서는 보관 기간 연장 동의나 삭제 의무 면제가 아니다.
- 긴급 유지보수: `costControl/monthlyBudget`의 `state.hold=true`를 운영자가 설정하면 이후 변경을 중단한다. 이미 나간 요청은 완료될 수 있으므로 함수 실행이 끝날 때까지 기다린 뒤 수동 작업한다.
- 복구할 때는 `state.resources`의 원래 서비스 scaling·예약 상태와 실제 현재 UID/리비전을 비교한다. 게임 서비스 설정을 먼저, 원래 ENABLED였던 예약만 나중에 복구한다. 직접 수정한 항목은 무조건 덮어쓰지 않는다. 토픽 중지/함수 제거만으로 게임이 자동 복구되지는 않는다.
- 실제 복구 확인 후에만 내부 비용 상태를 초기화한다. 초기화는 비용 보고를 지우지 않으므로 같은 달의 10만원 초과 통지가 다시 오면 재중단된다. 임시 수동 운영 중에는 observe/hold를 유지하고 이후 정책을 재확인한다. 게임 저장 문서를 초기화하지 않는다.
- 중단 기간에는 게임 재배포를 피한다. 배포가 수동 0 설정을 덮어쓸 수 있다. 필요하면 hold·상태 검토 후 재배포하고 비용 보호 설정을 다시 확인한다.
