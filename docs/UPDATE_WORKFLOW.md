# 앱과 서버 업데이트 기준

## 최신 업데이트 기준 · 0.81.0 / 2단계 준비

현재는 **0.81.0 코드·문서 준비 단계**다. 아래의 0.80.0·0.79.0 설명은 당시 기록이며, 상태나 미정 항목이 충돌하면 이 절과 [2단계 준비안](STAGE2_PREPARATION.md)을 우선한다. 테스트·빌드·Node 22/24·에뮬레이터의 실제 통과 범위는 [검증결과](../검증결과.md)의 0.81.0 기록을 확인한다.

진행 순서는 **보안·삭제 보완 → 비용 추정·별도 승인 후 서버 배포와 테스트 계정 실제 확인 → 랭킹 → 공개 정책 정합 → 최종 AAB**다. 단계별로 변경, 테스트·빌드, 미확인 항목, 정책 영향을 보고한다. 현재 서버 코드를 준비했다고 2단계 실제 운영 확인까지 완료한 것은 아니다.

이번에 확정한 정책은 다음과 같다.

- 기기 백업은 구버전 백업을 포함해 최대 10개다. 이전 초과분과 서로 다른 원본을 보존하며 자동 삭제하지 않는다. 확인한 항목만 개별 삭제하고 현재 진행 중인 저장은 유지한다.
- 신고는 KST 하루 5건, 같은 신고자·대상 UID·닉네임 세대에는 사유와 무관하게 1회다. 계정별 분당 변경 10회 제한도 유지한다. 신고 원문과 처리·복원 기록은 완료 후 90일, 미처리는 검토 완료까지 보관한다. 최소 중복 방지 값은 닉네임 변경 또는 양쪽 중 한 계정의 탈퇴까지 유지한다.
- 운영자 본인만 비공개 도구로 신고를 검토한다. 경고·강제 기본 닉네임 부여·기각·오조치 복원을 준비하며, 이의제기는 기존 앱 문의 이메일로 받는다. 일반 변경권은 여전히 미정이다. 사용자 callable에 관리 API를 추가하지 않는다.
- 삭제 재시도는 6시간마다, 만료 정리는 하루 1번이다. 미완료 최소 정리 작업은 성공까지 유지하고 성공하면 삭제한다. 함수와 예약 연결은 코드만 준비했으며 실제 작업은 실행하지 않았다.
- 월 비용 계획은 20만 원, 예산 알림 기준은 5만·10만·15만·20만 원이다. [최신 비용 추정서](SERVER_COST_ESTIMATE_2026-10-12.md)를 보고 별도로 승인받기 전에는 Blaze·예산·알림·함수·예약·IAM·콘솔 설정을 바꾸지 않는다. 알림이 지출을 자동 차단하는 것은 아니다.

0.81.0의 개발·운영 서버 배포와 운영 연결의 실제 Google 로그인, 관리자 IAM, 실제 Play Integrity 증명, 실기기 확인은 **미완료**다. 콘솔 변경은 사용자가 직접 하며, 실제 확인에도 기존 진행이 없는 테스트 전용 계정만 사용한다. 실제 사용자·개발 만렙 기록을 운영에 올리지 않는다.

방침 11·약관 8은 최종 문안 승인 전까지 유지한다. 공개 Docs를 수정하지 않으며 테스트 광고 ID, 저장 키·형식 38·migration·큰 금액 처리를 유지한다. 이번 준비 작업에서는 AAB를 만들거나 Play에 업로드하지 않는다. 기존 0.77.1·0.79.0 AAB도 중간 검증물이다. 1~4단계 완료 뒤에만 최종 AAB를 만들며, Play 업로드와 main 병합은 별도 확인한다.

실제 배포를 진행할 때는 [배포 순서서](SERVER_DEPLOYMENT_RUNBOOK.md)의 **에뮬레이터 → 개발 프로젝트 → 운영 프로젝트** 순서, 중단 조건, 되돌리기 절차를 따른다. 아래 일반적인 앱·서버 배포 설명만을 근거로 현재 승인 경계를 건너뛰지 않는다.

## 과거 준비 기록 · 0.80.0

보안·삭제 보완 → 비용 추정/사용자 승인 후 서버 배포·테스트 계정 실제 확인 → 랭킹 → 정책 공개 내용 정합 → 최종 AAB 순서다. 단계별 테스트/빌드/미확인/정책 영향을 보고한다. 기존0.77.1/0.79.0 AAB는 중간 검증용이다. 현0.80.0도 로컬 코드 검증 단계이며 운영 배포/AAB/Play 업로드가 아니다.

월20만원 계획 기준으로 예측한 뒤 Blaze·예산·함수/예약 설정을 승인받는다. 예약 삭제 작업은 코드만 준비돼 있으며 아직 실행되지 않는다. 공개 정책 문안 확정 전 방침11·약관8 번호를 올리지 않는다. 실제 사용자/개발 만렙 기록은 운영 검증에 쓰지 않는다.

API 호환성을 따질 때 App Check도 포함한다. 이 버전 서버는 등록된 Android 증명이 없는 이전 앱·웹 클라우드 요청을 거부한다. 현 운영Functions는 미배포이므로 기존 운영 저장API를 교체한 것은 아니다. 기존 앱이 실제 서버를 사용하는 상황에서는 배포 전 단계적 전환안을 별도로 마련한다.

## 변경 종류에 따른 배포 대상

앱과 서버는 변경된 쪽만 업데이트한다. 서버 변경이 없으면 AAB만, 앱 변경이 없고 기존 앱과 호환되면 서버만 배포할 수 있다.

| 변경 | AAB / Google Play | Firebase 서버 |
|---|---|---|
| 게임 화면, 그림, 음악, 앱에 들어 있는 병력/가격/전투 계산 | 필요 | 서버도 같은 게임 계산으로 저장 기록을 검사한다면 함께 변경 |
| 서버 저장 검증·삭제 재처리·호출 제한 수정 | 앱 통신 형식이 같으면 불필요 | 필요 |
| 로그인·클라우드·랭킹 같은 새 기능 | 대체로 필요 | 대체로 필요 |
| 개인정보 처리 변경 | 앱 안 안내 변경 시 필요, 공개 방침/Play 양식도 반영 | 처리 방식 변경 시 필요 |
| 기존 기록 검토·승인 같은 운영 데이터 작업 | 불필요 | 코드 배포 대신 권한 있는 운영 작업 |

현재 서버 검증기는 tools/prepare-server.mjs로 앱의 게임 규칙을 복사한다. 따라서 밸런스를 바꿀 때 서버 검증 영향도 함께 확인한다. 현재 구조에서 모든 밸런스 변경을 서버만으로 반영할 수는 없다.

## 두 곳을 함께 바꿀 때

1. 소스·정책·버전을 수정하고 개발 환경에서 검증한다.
2. 이전 앱의 API 요청과 저장 형식을 서버가 계속 읽는지 확인한다. 앱 업데이트는 모든 사용자에게 동시에 적용되지 않는다.
3. 호환되는 서버 변경을 먼저 배포하고 확인한다. 호환이 안 되는 변경은 기존 API를 남기고 새 API를 추가한다.
4. 최종 서명 AAB를 만들어 Play에 올린다. 운영 빌드에는 운영 Firebase 설정만 포함해야 한다.
5. 오류·삭제·저장 충돌·비용을 확인하고, 문제 시 되돌릴 코드와 API 호환 범위를 기록한다. 새 저장 데이터를 무조건 과거 코드로 되돌리지 않는다.

운영 프로젝트는 `budae-kiugi-prod`, 개발 프로젝트는 `budae-kiugi-dev`다. 배포 명령에는 프로젝트를 명시한다. 0.79.0은 앱 연결/빌드 준비이며 Functions 운영 배포, 과금 전환, Play 업로드는 아직 수행하지 않았다. 보안·삭제·랭킹·정책 공개 완료 후 최종 배포한다.

공식 참고: [Firebase 함수 관리](https://firebase.google.com/docs/functions/manage-functions), [환경별 프로젝트 분리](https://firebase.google.com/docs/projects/dev-workflows/general-best-practices).
