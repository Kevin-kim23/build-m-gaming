# 다른 PC에서 이어하기 · 서버 개발과 출시 준비

기준: 2026-10-12 KST / 앱 0.77.0 / 기능 커밋 `7fc2e2d` / 브랜치 `feat/firebase-server-test`.

이 문서는 사용자가 요청한 **남은 일·정책 수정·주의사항 인수인계**다. 이번 정리는 문서 작업이며 게임 기능, Firebase 설정, Play Console을 새로 변경하거나 출시하지 않는다. 완료 표시에는 실제 확인 근거가 있어야 한다. 아래의 미완료 항목을 문서가 있다는 이유로 완료 처리하지 않는다.

## 1. 가장 먼저 알아둘 것

- Google 로그인은 개발 웹에서 실제 성공했고 새 창에서도 유지됐다. **게임 기록은 아직 서버에 저장되지 않는다.** 다른 폰에서 기록·구매를 복구할 수 있는 상태가 아니다.
- Firebase `budae-kiugi-dev`는 개발용이다. Firestore 서울 리전은 준비됐지만 클라이언트 접근은 모두 거부한다. 인증 확인을 위해 이 규칙을 풀 필요는 없다.
- 기존 폰 기록을 유지하려는 사용자 의사가 있다. 로그인 추가·서버 이전·업데이트를 이유로 실제 기록을 초기화하거나 개발 만렙 저장으로 덮어쓰지 않는다.
- 서버 작업은 위 브랜치에 푸시돼 있다. `main`에는 병합하지 않았다. Git 동기화가 브라우저 저장·서명키·비공개 음원·로그인 세션까지 옮기는 것은 아니다.
- 오늘 업로드할 **새 서명 AAB는 이 작업에서 만들거나 검사하지 않았다.** 개발 APK 빌드 성공과 Play 업로드 준비 완료를 구분한다.
- 한국만 출시, 앱의 이용 대상은 만14세 이상이다. 대상 연령과 콘텐츠 등급은 별개다. 배포 국가/연령을 이번 서버 작업에서 바꾸지 않는다.
- 정책 관련 상세 할 일은 [계정·출시 정책 수정 목록](store/ACCOUNT_POLICY_TODO.md)에 있다. 이전 문서의 '서버 없음', '로그인 없음'은 당시 버전 기록일 수 있으므로 배포본과 비교한다.

## 3. 집 PC 시작 순서

게임 저장이 있는 기존 앱은 삭제하지 않는다. 먼저 저장소에서 `git status`를 확인하고 수정 중인 파일을 보존한다. 강제 reset/clean 또는 무조건 stash로 다른 작업을 밀어내지 않는다.

```powershell
git status
git fetch origin
git switch feat/firebase-server-test
git pull --ff-only origin feat/firebase-server-test
npm ci
npm run dev:firebase
```

로컬에 해당 브랜치가 없다면 switch 단계에서 `git switch --track origin/feat/firebase-server-test`를 사용한다. fast-forward가 불가능하면 커밋 차이를 확인하고 통합하며 강제 푸시하지 않는다. 먼저 `AGENTS.md`, 이 문서, [Firebase 연결 상세](FIREBASE_DEVELOPMENT.md)를 읽는다.

| 필요한 것 | Git으로 이동하는가 | 집에서 할 일 |
| --- | --- | --- |
| 코드·테스트·공개 Firebase 앱 설정·이 문서 | 예 | 같은 브랜치 최신 커밋 확인 |
| Firebase 콘솔 설정·Auth 사용자 | Git 파일 아님 | 같은 관리자 계정으로 개발 프로젝트 확인; 복제 프로젝트를 임의 생성하지 않기 |
| 기존 게임 저장·로그인 상태 | 아니요 | 각 기기/브라우저/포트의 별도 기록임을 확인 |
| 출시 업로드 키·암호 설정 | 아니요 | 집의 기존 키 사용; 채팅/공개 Git에 올리지 않기 |
| debug.keystore | 아니요 | 새 PC의 SHA-1/SHA-256을 개발 Android 앱에 등록 |
| 승인된 비공개 음원 | 아니요 | 기존 보관본을 복원하고 `npm run audio:verify` |
| JDK21·Android SDK·local.properties | 아니요 | `npm run android:doctor`, 필요 환경만 설정 |

게임은 `http://127.0.0.1:4196/`에서 연다. 저장을 읽지 않는 인증 전용 확인은 `npx vite --config tools/account-qa.config.mjs` → `http://127.0.0.1:4214/__account`다. 두 주소의 로그인/게임 저장은 서로 자동 복사되지 않는다.

## 4. 오늘 올릴 AAB: 가장 먼저 마칠 점검

현재 구현은 **개발용 로그인 기능을 일반 출시 빌드에서 제외**한다. 그러나 공통 방침과 라이선스에는 개발 테스트 설명이 남아 있다. '개발용 문구까지 모두 제거됨'이나 '최종 AAB 검증 완료'로 보고하지 않는다.

- [ ] **배포할 코드 확정:** 업로드 대상 브랜치·커밋·버전을 정한다. 서버 브랜치를 무조건 main에 합치지 않는다. 출시 작업과 서버 개발이 같은 `dist/`·Android assets를 동시에 덮어쓰지 않게 순서대로 빌드한다.
- [ ] **정책 문구 정리:** 로그인 없는 출시본의 앱 방침/약관/스토어 설명을 실제 동작에 맞춘다. 개발 문서를 제거하더라도 실제 AdMob/UMP 처리 고지는 유지한다. [정책 목록 A](store/ACCOUNT_POLICY_TODO.md)를 따른다.
- [ ] **키·자산 준비:** 집의 기존 업로드 키와 비공개 음원을 확인한다. 다른 PC라는 이유로 새 업로드 키를 만들거나 기존 앱을 삭제하지 않는다.
- [ ] **버전 확인:** `package.json`을 기준으로, Play에 이미 업로드한 versionCode보다 큰지 확인한다. 이 문서만 추가한 커밋은 기능 변경이 없어 0.77.0을 유지한다.
- [ ] **검증/빌드:** `npm ci` → `npm test` → `npm run android:doctor` → `npm run android:release`. 이 release 명령은 음원 검사·일반 웹 빌드·Capacitor 동기화·서명 AAB/APK·lint를 수행한다. 자동으로 Play에 업로드하지 않는다.
- [ ] **개발 설정 제외:** 출시 assets에 `firebase-development-build.json`이 없어야 한다. 인증 메뉴/실행 청크, 개발 프로젝트 인증 리소스, Firebase Authentication 네이티브 실행 의존성이 없는지 검사한다. 개발 자산이 남아 있으면 Gradle이 실패해야 하며 차단 코드를 지우지 않는다.
- [ ] **단순 문자열 검사의 한계:** 라이선스 고지의 Firebase 이름, 미사용 플러그인 설정 이름과 실행 SDK를 구분한다. Firebase라는 단어가 있다는 사실만으로 개발 로그인 실행이 포함됐다고 판정하지 않는다. 반대로 메뉴만 숨겼다는 이유로 SDK/통신까지 제외됐다고 판정하지 않는다.
- [ ] **최종 파일 검사:** `android/app/build/outputs/bundle/release/app-release.aab`의 생성 시각·SHA-256·서명·패키지 `com.dongramco.budaekiugi`·versionCode·manifest/권한·자산을 확인하고 bundletool 검증. 실패 후 남은 오래된 산출물을 업로드하지 않는다.
- [ ] **설치 확인:** Play 테스트 트랙 설치본에서 기존 기록 유지, 시작 화면/터치/상점/전투, 백그라운드 복귀, 오프라인 수입, 광고 동의/거부와 완료 보상을 확인한다. 개발 로그인 메뉴가 보이지 않아야 한다.
- [ ] **게시 확인:** 업로드·검토 제출·트랙 배포·사용자 설치를 따로 기록한다. 업로드만으로 배포 완료라고 하지 않는다. 이번 문서 작업에서는 어느 것도 실행하지 않는다.

개발 APK는 `.dev` 패키지이며 출시 앱과 저장이 별개다. `app-debug.apk` 또는 `app-unsigned.aab`를 Play 제출용으로 사용하지 않는다. `npm run android:sync:firebase`는 **개발용**이다. 일반 출시 절차: [ANDROID_RELEASE](ANDROID_RELEASE.md). 이전 빌드의 절대 경로·해시는 이번 새 파일의 증거가 아니다.

## 5. 서버 기능을 이어 만드는 순서

각 단계는 작은 커밋으로 작업하고, 성공 기준을 통과한 뒤 다음 단계로 간다. 정책·삭제 설계는 마지막에 몰아서 하지 말고 데이터 추가 단계와 같이 준비한다.

### 1) 로그인 실기기 확인과 닉네임

- [ ] Android `.dev` 실제 폰에서 선택/취소/네트워크 끊김/복귀/재실행/로그아웃 확인. 다른 debug 키와 미등록 지문 오류를 구분한다.
- [ ] 로그인 선택 여부를 분명히 하고, 첫 프로필 저장 전에 처리 정보와 필요한 선택을 안내한다. Google 비밀번호·연락처·메일함 접근을 요구하지 않는다.
- [ ] 닉네임 길이·문자·공백/정규화·금칙어·운영자 사칭을 서버에서 검증한다. 화면 HTML 삽입, 서버 검증 우회, 변경 연타도 검사한다.
- [ ] 중복 허용/식별번호, 변경 간격·비용은 사용자에게 먼저 정한다. 정하지 않은 수치를 확정 사양처럼 넣지 않는다.
- [ ] 완료 기준: 재로그인/다른 기기에서 같은 UID의 닉네임 복원, 타인 프로필 수정 거부. 이메일·Google 실명·사진을 공개 닉네임/랭킹에 자동 노출하지 않는다.

### 2) 기존 기록 연결·서버 저장·충돌 처리

- [ ] 데이터 구조·접근 규칙·서버 검증을 설계하고 Firebase Emulator에서 본인 접근 허용/타인 읽기·쓰기 거부부터 시험한다. 인증됐다는 이유로 전체 데이터 읽기/쓰기를 허용하지 않는다.
- [ ] 게스트 기록을 처음 계정에 연결할 때 원본 보존 및 동의/선택 절차를 둔다. 서버와 기기에 둘 다 진행이 있으면 덮어쓰기 전에 선택·충돌 해결을 제공한다. 골드/병력을 단순 합산하지 않는다.
- [ ] 로그아웃/다른 계정 로그인 시 저장 큐·재시도·진행 중 요청을 UID와 세션 단위로 분리한다. A 계정 기록이 B 계정에 저장되지 않게 한다.
- [ ] 로컬 저장 형식38, 키 `budae-kiugi-recruits-v3`, 구버전 migration을 보존한다. 구조 변경 시 버전과 구버전 회귀 테스트를 함께 갱신한다.
- [ ] 골드 상한은 현재 **1,000자(10^27)**다. 전력도 BigInt를 사용한다. 서버 경계에서는 검증된 큰 정수 문자열을 사용하고 `money.js`/`serializeSave`를 재사용한다. Firestore 숫자나 Number로 무조건 변환하지 않는다.
- [ ] 저장 revision/서버 시각/원자적 갱신·기기 동시 접속 정책, 재시도 상한·간격, 저장 크기·빈도 제한을 둔다. 터치마다 서버에 저장하거나 영구 재시도하지 않는다.
- [ ] 구버전 앱이 새로운 서버 저장을 덮어쓰지 못하게 최소 호환 버전을 둔다. 오프라인·앱 강제 종료 중 저장과 계정 전환도 검사한다.
- [ ] 오프라인 최대8시간, 물약 효과 시간, 보상 수령/광고 중복 콜백을 함께 검증한다. 폰 시계만으로 보상·결제·랭킹을 신뢰하지 않는다.
- [ ] 완료 기준: 기기 A→B 복원, 두 기기 충돌, 통신 재시도, 안전 정수 경계/상한 저장, 과거 저장 복구에서 손실·중복 지급 없음.

### 3) 정식 탈퇴·운영·보안

- [ ] 현재 개발 계정 삭제는 Auth만 지운다. 프로필·게임 저장·랭킹·관련 공개 자료까지 지우는 재시도 가능한 삭제 절차로 확장한다.
- [ ] 재인증, 계정 변경 중 잘못된 삭제 방지, 삭제 실패/진행 안내, 삭제된 계정의 옛 로컬 큐가 서버 기록을 되살리지 못하는 처리를 둔다. 법정 보관 예외는 범위·근거·기간을 별도로 확정한다.
- [ ] 앱을 다시 설치하지 않아도 요청할 수 있는 외부 삭제 페이지, 요청자 확인·처리 기록·신고/닉네임 이의제기 절차를 만든다.
- [ ] 관리자 권한 최소화·2단계 인증·복구 수단·서버 백업/실제 복구 연습·오류 확인·장애 공지 경로를 정한다. 개인정보/토큰을 공개 Git·스크린샷·오류 로그에 남기지 않는다.
- [ ] App Check/Play Integrity 적용 범위를 검토하고 실제 폰 검증 후 단계적으로 적용한다. 이를 로그인 권한 검사나 게임 치트 방지의 대체물로 취급하지 않는다. 디버그 토큰은 공개하지 않는다.
- [ ] 무료 할당량, 서버 함수/예약 작업에 필요한 요금제, 월 비용 추정·예산 알림·요청 제한을 확인한다. 예산 알림을 자동 과금 상한으로 오해하지 않는다. 유료 전환은 비용과 범위를 설명하고 진행한다.

### 4) 전력 랭킹

- [ ] 전력 기준, 상위100명·내 순위·공동 순위, 마지막 갱신 시각, 오전9시 KST(UTC 00시) 갱신을 구현한다. 공동순위 다음 번호 규칙은 확정한다.
- [ ] 서버가 검증한 전력만 집계한다. 클라이언트가 전송한 숫자/계급/개발 여부를 그대로 신뢰하지 않는다. 공개 랭킹에는 닉네임·순위·허용된 게임 수치만 둔다.
- [ ] 큰 전력을 문자열로 보관할 경우 단순 문자열 정렬이 숫자 순서와 다르다는 점을 처리한다.
- [ ] 개발 만렙 계정은 서버가 관리하는 구분으로 제외한다. **과거 로컬 기록이 정당하게 플레이된 것인지 완전히 증명할 수는 없다.** 정상 테스터 기록 보존과 랭킹 참여 기준을 별도로 정하고 기록을 임의 삭제하지 않는다.
- [ ] 하루 집계는 중복 실행해도 결과가 중복 생성되지 않게 한다. 전체 집계를 마친 스냅샷만 공개하고 실패하면 이전 순위·갱신 시각을 유지한다.
- [ ] 완료 기준: 동점/탈퇴/제재/닉네임 변경/최대 전력/서버 장애/갱신 경계 시각 테스트. 일반 사용자가 자기 순위나 다른 사용자의 점수를 직접 쓸 수 없어야 한다.

### 5) 운영 서버 연결과 결제 복원

- [ ] 개발 프로젝트를 운영에 그대로 쓸지 별도 운영 프로젝트로 옮길지 결정한다. 새 Firebase 프로젝트에서는 UID·Auth·Firestore가 자동 이관되지 않는다. 사용자 수/기록/UID 매핑·소유권을 검증한 이전/되돌리기 계획이 필요하다.
- [ ] 정식 Android 앱 등록과 Play **앱 서명 인증서** 지문을 확인한다. 업로드 키 지문·개발 키 지문과 구분하고 실제 Play 설치본에서 로그인한다.
- [ ] Google 게임 로그인과 Play 구매 복원은 별도 기능이다. Play 결제 토큰/상품/결제 상태의 서버 검증, 중복 지급 방지, 보류·취소·환불/철회·재설치를 구현한다. 단순 로컬 `보유=true`를 유료 구매 증명으로 쓰지 않는다.
- [ ] 이미 지급된 무료 테스트 자동터치의 영구 보유는 보존하고 실제 구매 권한과 구분해 이관한다. 이 무료 권한을 유료 구매 영수증으로 바꾸지 않는다. 게임 계정/Play 계정이 다를 때 권한 연결·계정 전환 정책을 정한다.
- [ ] 상품 추가 전 사업자·결제 프로필·세금·판매자 표시·환불/미성년자 구매 관련 적용 요건 및 Play 정책을 확인한다. 계정 삭제가 자동 환불이나 Google 계정 삭제를 뜻한다고 안내하지 않는다.

## 6. 테스트와 변경 보고에 남길 것

- 기능 변경 시 `npm test`·`npm run build`, 저장/계정/정책 관련 집중 테스트, 새 기능의 실제 경로를 확인한다. 기존 실패를 숨기거나 테스트만 느슨하게 바꾸지 않는다.
- SDK 추가 시 사용 라이선스/고지를 갱신한다. 현재 생성기는 release/debug 합본이므로 `:app:exportNoticeDependencies -PnoticeVariant=all`을 사용한다. [라이선스 안내](licenses/README.md).
- Firebase 규칙/함수는 AAB 업로드로 자동 배포되지 않는다. 별도로 검증·배포하고 해당 버전과 앱 호환 범위를 기록한다. Git 브랜치는 실제 Firebase 프로젝트를 자동 분리하지 않는다.
- 버전·커밋·테스트 수/실패·빌드 종류·실폰 여부·정책 공개 상태·최종 파일 해시·다음 할 일을 보고한다. 공개 저장소에는 실제 사용자 저장/구매 토큰/테스터 이메일/비밀키를 첨부하지 않는다.
- 게임 기능을 바꾸면 버전을 올리고 README/검증결과/CONTINUE를 갱신한다. 순수 문서 정리는 버전을 불필요하게 올리지 않고 문서 작업임을 기록한다.
