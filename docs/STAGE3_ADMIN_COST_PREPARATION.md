## 파트A 진행 조건

- 최신 사용자 위임: AI가 쉬운 콘솔 조작·화면 이동·계정 생성·역할 정의 준비를 진행하고 개발 프로젝트를 직접 확인한다. 이메일·비공개 값 입력과 민감 권한 저장은 사용자가 직접 한다. 기존의 모든 클릭 사용자 직접 규칙보다 최신 지시가 우선한다. 운영 별도 월10만원이 승인되어 파트B 코드·문서 준비를 진행한다. 운영 콘솔/배포는 계속 금지다.
- 사용자 이메일, 서비스 계정 숫자 고유 ID, 토큰/키, 결제계정 번호, 예산 ID를 화면에서 가리고 공유한다. 실제 값은 기록하지 않는다.
- 호출 계정에는 프로젝트 전체 Owner/Editor/Firestore 권한을 부여하지 않는다. 사용자의 Service Account Token Creator(임시 인증 발급 권한)는 호출 계정 하나에만 적용한다.
- 실행 계정은 Firestore(DB) 작업에 필요한 권한만 검토한다. 서버 DB 권한을 컬렉션별 보안 규칙으로 제한된다고 오해하지 않는다. Auth 계정 삭제 권한은 부여하지 않는다.
- 호출 계정 Cloud Run Invoker(함수 호출 권한)는 실제 관리자 서비스 배포 후 그 자원에만 준다. allUsers/allAuthenticatedUsers에 관리자 권한을 주지 않는다.
- 두 계정 모두 키 생성/다운로드 금지. API 사용 설정은 상태 확인 후 필요할 때 사용자 승인·사용자 직접 진행이다.
- 로컬 설정 파일은 아직 변경하지 않았다. server/.env.<프로젝트ID> 등에 값을 넣기 전에 파일 위치·값의 종류·Git 제외 확인을 설명하고 별도 승인받는다. 숫자 ID 등을 예제에도 실제 값으로 쓰지 않는다.
- 프로젝트 불일치·키 요구·프로젝트 전체 권한 요구·예상 밖 비용·이해 못 한 단계면 중단한다. 잘못 부여한 권한은 정확한 대상 권한만 제거하는 계획을 먼저 검토하며, 계정 삭제로 임의 복구하지 않는다.

### PASS 체크리스트 — 콘솔 설정 확인 완료, 실제 서버 동작 미검증

1. 호출 계정과 실행 계정이 별개로 존재한다: PASS. 생성 후 목록/상세에서 직접 확인.
2. 두 계정 키 탭이 비어 있다: PASS. 각 키 탭의 표시할 행 없음 직접 확인. 실행 계정 목록의 일시적 로딩 실패는 상세 키 탭과 재조회 목록에서 해소 확인.
3. 사용자에게 직접 부여한 Token Creator가 호출 계정 하나에만 있다: PASS. 호출 계정은 상속 없음으로 직접 부여, 실행 계정과 기존 Firebase 관리 계정에서는 사용자 소유자 상속만 확인했다. 기존 프로젝트 소유자의 관리 권한까지 제거하거나 전체 보안 감사가 끝났다는 의미가 아니다.
4. 실행 계정에는 Firestore 맞춤 역할 하나만 있고 Auth 삭제 권한이 없다: PASS(콘솔 역할 정의/부여 기준). 아래6개 외 IAM/Auth 권한 없음. 실제 Auth 요청 거부 테스트는 배포 후 별도다.

### 실제 생성·권한 범위와 주의점

- 맞춤 역할 이름: `Moderation Firestore Runtime`, ID `moderationFirestoreRuntime`, 개발 검증용 베타. 포함 권한: `datastore.databases.get`, `datastore.entities.get`, `datastore.entities.list`, `datastore.entities.create`, `datastore.entities.update`, `datastore.entities.delete`.
- 서버 moderation-service.js와 database.js의 신고 조회·이름 변경/복원·정리 작업이 문서 CRUD/검색/트랜잭션을 사용함을 읽고 공식 API 권한표와 대조했다. 실제 서비스에서 충분한지는 배포 뒤 합성 신고 처리로 확인해야 한다.
- 범위는 개발 프로젝트의 Firestore 데이터 작업이다. 신고 컬렉션에만 제한되는 권한은 아니다. Auth 사용자 삭제·DB 전체 삭제·인덱스 관리·IAM 관리는 포함하지 않는다. 별도 수집 정보나 앱 권한을 추가하지 않았다.
- 기존 Firebase 관리 계정의 프로젝트 범위 Token Creator 상속과 사용자 Owner 상속을 발견했다. 이번에 만든 권한이 아니며 기존 서비스 영향 때문에 임의로 제거하지 않았다. 사용자만 모든 대리 인증을 할 수 있다고 주장하지 않는다. 기존 서비스 계정 권한 검토는 별도 과제로 남긴다.
- 관리자 Cloud Run Invoker, 함수 배포, 비용 보호 계정·Pub/Sub, 운영 콘솔, 로컬 환경 파일은 아직 변경하지 않았다.
- 되돌릴 때는 이번에 추가한 호출 계정의 직접 Token Creator 부여와 실행 계정의 맞춤 역할 연결만 검토 후 회수한다. 기존 기본 계정의 상속 권한을 임의로 지우지 않는다. API 화면은 Credentials API 사용 중지가 IAM API에도 영향을 준다고 안내하므로 단순 되돌림으로 API를 끄지 않는다.

### 키 파일과 임시 인증 — 사용자 설명

이번 구성에서는 서비스 계정 JSON 키를 만들거나 다운로드하지 않는다. 사용자는 자신의 Google 계정으로 인증하고 호출 계정의 단기 인증을 발급받는다. 임시 인증도 만료 전에는 민감한 값이므로 채팅/로그/Git에 출력하지 않는다. 장기 개인 키 파일을 배포·백업할 필요를 없애는 방식이며, 사용자 로그인 정보 보호는 여전히 필요하다. 서버의 실행 계정도 배포 환경에 연결된 신분으로 인증하고 키 파일을 넣지 않는다.

APK/AAB의 Android 업로드/앱 서명키는 서버 인증과 별개다. 기존 .jks/.keystore를 새 서버 설정 때문에 다시 만들거나 교체하지 않는다. 기존 업로드 키는 저장소 밖 개인 접근 제한 폴더와 암호화된 별도 백업으로 보관하고 비밀번호는 분리한다. Play App Signing 사용 시 앱 서명키와 업로드 키의 역할도 구분한다. 이번 작업에서는 Android 키나 인증 캐시를 읽거나 만들지 않았다.

공식 설명: [서비스 계정 대리 인증](https://docs.cloud.google.com/iam/docs/service-account-impersonation), [Android 앱 서명](https://developer.android.com/studio/publish/app-signing).
