# 개발 부분 배포 재개 비교안 · 0.83.18

2026-10-13. 이번 승인은 읽기·원인 조사·계획 준비만이다. 실제 재배포/삭제/IAM/새 읽기 허용 추가 없음. 기존 함수와 서비스를 보존한다. 아래 시간은 작업 추정이며 Google 대기 및 사용자 승인 시간을 보장하지 않는다.

## 실패 필드

실제 실패 필드 확정: 미확인. 기존 실행기는 여러 검사를 response-shape로 합쳤고 해당 응답은 저장하지 않았다. 따라서 확정 필드 이름을 만들어 말하지 않는다.

가짜 응답에서 재현한 후보 필드: response.url. 나머지 조건을 동일하게 둔 상태에서 경로가 없는 URL은 통과, 함수 경로가 있는 URL은 실패한다. 실제 URL 값은 조회/기록하지 않았다. 이것이 실제 요청17의 실패 필드였다는 증거는 아직 없다. 초기 합성 시 실제 API가 채우는 실행 계정을 null로 둬 두 사례 모두 실패했으며, 합성 실행 계정을 채운 뒤 대조 실험에서 위 차이를 확인했다. 두 실험 모두 외부전송0.

직접 소스 근거: tools/firebase-guard/deployment-session.cjs의 operation 완료 분기에서 response.name/buildConfig.runtime/serviceConfig.maxInstanceCount/serviceAccountEmail/service 및 response.url 검사. firebase-tools15.33.0 lib/deploy/functions/release/fabricator.js:461은 생성 결과 url을 사용하며 루트 경로 강제를 두지 않는다. 특정 원인 확정은 향후 승인된 단일 함수/operation 읽기 또는 콘솔에서 해당 메타데이터를 안전하게 확인한 뒤 진행한다. 재배포를 진단 수단으로 반복하지 않는다.

## 다음 승인 단위

지금 사용자 할 일 하나: A/B 방향 선택. A는 기존 원칙 유지, B는 공식 CLI의 동작 차이를 검토하되 아직 안전 원칙 변경 승인은 아니다. 선택 후 구체적인 수정/요청 목록과 보호 검증 결과를 제시한다. 실제 배포 실행은 그 뒤 최종 승인 및 사용자 확인 문구 입력이 필요하다. 계획서만으로 새 GET·IAM·배포 권한을 얻지 않는다.

은행 비유: A는 첫 창구 업무가 끝난 지점에서 전표를 검증해 이어가는 방식, B는 공식 창구가 기존 계좌 갱신과 신규 개설을 관리하는 방식이다. operation은 서버 작업의 진행 상태, revision은 배포된 실행 버전이다.
