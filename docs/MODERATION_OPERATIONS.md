# 닉네임 운영 도구 · 준비안 · 2026-10-12

사용자는 **본인만 신고를 검토**하고, 조치는 **경고·강제 기본 닉네임 부여**로 정했다. 잘못된 신고는 기각하고 오조치는 복원할 수 있도록 준비한다. 이의제기는 기존 문의 이메일로 받으며, 처리·복원 기록은 완료 후 90일 보관한다.

현재는 코드 준비 상태다. 실제 관리자 권한 설정, 배포, 관리자 로그인과 신고 처리는 수행하지 않았다.

## 비공개 경로와 사용 순서

moderateNicknames는 onRequest 방식의 비공개 HTTP 함수이며, 사용자 callable이 아니다. IAM의 private 호출 제한과 Google 서명 ID 토큰의 발급자·대상·단일 주체 검증을 함께 사용한다. 필수 설정이 비었거나 일반 Firebase 사용자 토큰을 보내면 거부한다. 사용자 앱에는 관리 버튼이나 관리 API가 없으며, 랭킹 승인·계정 정지 API도 추가하지 않는다.

로컬 도구 **tools/moderation-admin.mjs**는 목록 조회(list), 상세 조회(inspect), 처리(resolve), 복원(revert)을 제공한다. **변경 명령은 --confirm이 없으면 미리보기만 표시하고 인증 정보를 읽거나 서버에 요청하지 않는다.** 응답이 불명확하면 같은 actionId로 재시도하여 중복 처리를 피한다. 실제 권한을 준비하기 전에는 --help나 합성 입력의 변경 미리보기만 확인한다.

권한 설정과 실제 검증을 마친 뒤 운영자는 다음 순서로 처리한다.

1. 미처리 신고 목록과 상세 내용을 확인한다.
2. 신고 당시 이름과 현재 이름·변경 세대가 같은지 확인한다.
3. 승인된 금칙 범위에 해당하는지 직접 판단하고 경고, 기본 닉네임 부여, 기각 중 하나를 선택한다.
4. 변경 미리보기를 검토한 뒤 확인하여 실행한다.
5. 결과가 불명확하면 새 조치를 만들지 않고 같은 actionId로 재시도한다.

서버는 운영자가 선택한 reportId로 대상을 찾는다. 임의의 대상 UID를 입력하여 다른 계정을 제재하는 경로는 두지 않는다. 자유문장 메모나 증거 파일을 받지 않으며, 정해진 사유 값과 조치 기록만 처리한다.

강제 변경 시 서버가 중복을 확인한 기본 닉네임을 즉시 부여한다. 일반 변경권이나 무료 변경 횟수는 신설하지 않는다. 이용자는 다음 프로필 조회 때 경고·기본 이름 부여 안내와 기존 문의 주소를 확인한다. 메일이나 푸시로 조치를 알리는 기능은 없다.

## 상태·처리 기록·복원

- 신고 상태는 pending에서 resolved 또는 dismissed로 바뀐다. 최초 처리에서는 검토한 신고 version과 닉네임 변경 세대를 대조하여 동시에 들어온 처리나 오래된 이름에 대한 조치를 거부한다. 프로필 moderationVersion은 조치마다 증가하며, 오조치 복원 때 해당 조치 이후 다른 조치가 없었는지 대조하는 데 사용한다.
- 경고와 기본 이름 부여는 운영자가 검토한 신고에만 적용한다. 이름 변경 세대인 nicknameRevision은 이름을 되돌릴 때도 증가한다. 이전 세대의 중복 방지 값은 정리한다.
- 처리 기록에는 조치 ID, 신고·당사자 연결, 행위자 해시, 조치 종류와 시각, 변경 전후의 최소 닉네임·변경 번호·안내, 복원 연결과 정리 상태를 보관한다. 골드·병력·전체 게임 저장·로그인 토큰·이메일 본문은 복사하지 않는다.
- 복원은 이후 다른 조치가 없고 현재 닉네임과 소유권이 예상 상태와 일치할 때만 가능하다. 기존 이름을 다른 계정이 소유하면 복원을 거부하고 양쪽 계정 자료를 보존한다.
- 처리·복원 기록은 각 처리 완료 후 90일에 만료된다. 그 자료가 필요한 자동 복원은 만료 후 보장하지 않는다. 미처리 신고는 검토가 끝날 때까지 보관한다.
- 이름 변경 뒤 중복 정보 정리가 일부 실패하면 프로필 변경은 이미 반영되었다는 점을 구분한다. 같은 actionId의 재시도나 예약 재처리로 정리를 이어간다.
- 정리 실패 때문에 신고 원문이나 처리 기록의 90일 보관 기간을 늘리지 않는다. 별도 moderationCleanup에 당사자 연결·이전 세대·시각 등 최소 정리 정보만 남겨 성공할 때까지 재처리하고, 성공하면 이 작업 기록을 삭제한다. 여기에는 닉네임 원문이나 신고 사유가 없다.
- 신고자나 대상이 탈퇴하면 관련 신고, 중복 방지 정보, 처리 기록, 정리 작업을 삭제한다. 삭제 완료 확인 기록의 90일과 신고 원문 보관의 90일은 서로 다른 자료에 적용하는 기준이다.

## 최소 권한·2단계 인증·복구 — 사용자 직접 설정, 현재 미설정

1. 본인 Google 계정에 2단계 인증을 설정하고 보안키·패스키와 별도 복구 수단을 준비한다. 복구 코드, 비밀번호, 토큰은 채팅·Git·작업일지에 쓰지 않는다.
2. 관리자 호출 전용 서비스 계정과 실제 DB에 접근하는 함수 실행 계정을 분리한다. 호출 계정에는 해당 비공개 Cloud Run 함수의 run.invoker 권한만, 본인 계정에는 그 호출 계정의 단기 토큰 발급 권한만 부여하는 안을 검토한다. 본인 외 임의의 Editor·Owner나 플레이어에게 관리 권한을 주지 않는다.
3. 로컬에서는 승인 후 본인이 설정한 서비스 계정 대리 인증 방식의 ADC를 사용한다. 서비스 계정 JSON 비밀키는 다운로드하거나 저장소에 넣지 않는다. 함수 URL과 주체 설정은 비공개 환경에서 프로젝트별로 구분한다.
4. MODERATION_ADMIN_AUDIENCE에는 정확한 비공개 함수 URL, MODERATION_ADMIN_SUBJECT에는 승인한 호출 계정의 Google 숫자 subject를 설정한다. 이메일이나 클라이언트가 보낸 admin:true 값으로 권한을 판단하지 않는다.
5. Cloud Run의 IAM 인증에는 X-Serverless-Authorization, 함수 내부의 서명 검증에는 Authorization 헤더를 사용한다. 두 헤더의 원문을 로그·오류·분석에 기록하지 않는다. 관리 도구도 토큰을 화면에 출력하지 않는다.
6. 함수 실행 계정에는 필요한 Firestore 작업 권한만 검토하며, 이 관리자 함수에 Auth 계정 삭제 권한을 부여하지 않는다. Firestore 서버 IAM만으로 컬렉션별 접근을 완전히 분리할 수 없으므로 코드의 범위 검사와 IAM 변경 감사를 함께 유지한다. 클라이언트의 Firestore 직접 접근은 계속 거부한다.
7. 계정 분실이나 침해가 발생하면 본인이 2단계 인증 복구 → 관리 호출 권한 회수·호출 계정 교체 → 변경 기록 확인 → 개발 환경에서 거부·성공 재검증 순서로 복구한다. 비공개 경로를 임시로 공개하거나 2단계 인증을 상시 해제하지 않는다.
8. IAM·ADC·주체 설정을 실제로 적용하고 본인의 호출 성공과 다른 계정의 거부를 확인하기 전에는 운영 준비 완료로 표시하지 않는다. 이번 작업에서는 해당 설정을 변경하지 않았다.

현재 비공개 HTTP 코드만으로 함수의 기본 실행 서비스 계정이 최소 권한 계정으로 자동 분리되지는 않는다. 별도 실행 계정 생성과 배포 옵션은 비용·권한 설정 승인안에 포함하고, 실제 IAM 적용 후 검증한다.
